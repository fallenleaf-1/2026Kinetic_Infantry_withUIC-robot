## 0. 使用说明

### 0.1 阶段划分（按你的实际工况：**先让底盘板单独跑起来测试，双板验证放后面**）

| 阶段 | 含义 | 能否**只烧底盘板**就验证 |
| --- | --- | --- |
| **A** | 底盘单板本地可直接修的 P0 —— **改完即可编译烧录用着测试** | ✅ 可以 |
| **B** | 底盘板本地电机安全 | ✅ 可以 |
| **C** | 底盘板本地健壮性 | ✅ 可以 |
| **D** | **必须云台板在位 / 双板联机**才能做或验证（⏸ 暂缓） | ❌ 不可以 |
| **E** | 文档基线（不阻塞代码修改，但**必须在改代码前**处理） | — |

> **关键前提**：**A-D 全部不改变板间 CAN 报文格式与长度**。因此你可以在**云台板固件不重刷**的情况下，只烧底盘板新固件并与旧云台板固件互联运行。

> ⚠️ **但"能单独验证"≠"不影响云台板"**：`Src/`、`application/robot_task.h`、`modules/daemon/daemon.c`、`modules/can_comm/can_comm.c` 等文件被**双板共同编译**。改这些文件的代码，云台板**编译同一份源码时行为也会变**——所以每项都标注了「跨板影响」，并在双板阶段统一回归。

### 0.2 口径

| 概念 | 含义 |
| --- | --- |
| **P0** | 不修会失控、或故障发生时完全不可见，必须在下次上电/上台架前处理 |

### A.1 明细：S6 的 7 处

| 位置 | 错误 |
| --- | --- |
| `application/robot_task.h:80,97,116,133,163` | `LOGERROR("...[%f]", &xxx_dt)`：`%f` 不受支持（`bsp_log.h:37,55`）**且传地址**，双重错误 |
| `modules/can_comm/can_comm.c:77` | `&comm->can_ins->rx_id` 传地址 |
| `bsp/can/bsp_can.c:80` | `&config->tx_id, &config->rx_id` 传地址，且字符串含多余 `}`：`"[}bsp_can]"` |

- **不要顺手改这两处**（源报告已撤销的误报）：`dji_motor.c:155`（实参无取址）、`bsp_can.c:73`（该行无格式参数）。
- **改法**：7 处统一改为**传值 + 受支持的格式符**（`%d`/`%u`；浮点先转整数毫秒）。
- **为何与 S2/S3 同批**：这 7 处恰是 S2/S3 触发时会打印的日志 —— **不修则总线故障完全不可见**。

### A.3 决策：`CANTransmit()` 超时（`bsp_can.c:106-119`）

- **问题**：`bsp_can.h:63` 明确 timeout 单位 ms；底盘板实际启用 **4 个发送组 `[0][1][3][4]`**，最坏 4 次 × 约 1 ms = **4-8 ms 阻塞**，而 MotorTask 周期仅 **1 ms**（`robot_task.h:98`）。全部调用方丢弃返回值。
- **方案 A（最小改动）**：超时改 µs 量级，把单次等待压到远小于任务周期。
- **方案 B（推荐，与非阻塞趋势一致）**：`HAL_CAN_AddTxMessage` 失败即返回并计数，**不做忙等**。
- **方案 B 的安全性已核**：`dji_motor.c:313`、`power_control.c:333`、`can_comm.c:121` 等**全部调用点都忽略返回值**（源码已确认），故不存在"依赖发送成功才继续"的时序假设被破坏。

### A.4 决策：S2 Bus-Off 恢复（`Src/can.c:48,80`）

- **现状**：两路均 `AutoBusOff = DISABLE` + `AutoRetransmission = ENABLE`；未启用错误中断；全树无 `HAL_CAN_GetError`/`HAL_CAN_ResetError`；控制器进入 Bus-Off 后停在 `HAL_CAN_STATE_LISTENING`。
- **方案 A（推荐先上，一行）**：`AutoBusOff = ENABLE`，交硬件自动恢复。
- **方案 B（后续加固）**：启用错误中断 → `HAL_CAN_GetError()` 检测 → **`HAL_CAN_Stop()` → 复位状态 → `HAL_CAN_Start()`** 完整序列。
  > **重要**：**单纯重调 `HAL_CAN_Start()` 无法恢复**（HAL 要求 `hcan->State == HAL_CAN_STATE_READY`，而 Bus-Off 后状态停在 LISTENING 且无人复位）。
- **两者共同要求**：`CANTransmit` 调用点至少记录失败计数（与 A.3 共享 `busy_count` 诊断）。
- **需台架**：人为制造 Bus-Off，验证恢复路径与失败计数。

## 2. 阶段 B：底盘板本地电机安全

> 同样**只烧底盘板**即可验证。

### B.1 [x] F7 无 `PIDReset` —— 停止→使能窜车 ⚠️ **本清单最重要的实施修正**

- **位置**：`dji_motor.c:210-218,303-305`；`chassis.c:426-447`
- **问题**：全树无 `PIDReset`；`DJIMotorStop/Enable` 只改 `stop_flag`，PID 的 `Iout/ITerm/Last_*` 全部保留；零力↔运行反复切换时积存量在重新使能瞬间一次性释放（「窜车」）。
- **方案**：新增 `PIDReset(PIDInstance *)`，复位**计算区**、**保留配置区**：

  | 保留（配置） | 复位（状态） |
  | --- | --- |
  | `Kp/Ki/Kd/MaxOut/DeadBand/Improve/IntegralLimit/CoefA/CoefB/Output_LPF_RC/Derivative_LPF_RC` | `Measure/Last_Measure/Err/Last_Err/Last_ITerm/Pout/Iout/Dout/ITerm/Output/Last_Output/Last_Dout/Ref/ERRORHandler` |

  实现可直接 `memset` `controller.h:73` 之后的计算区（该区块已在源码中显式标注 `// for calculating`），或逐字段赋值。
- ⚠️ **必须只在一处调用**：**在 `DJIMotorStop()` 里调用一次**；**`DJIMotorEnable()` 不重置**。
  **原因**：`ChassisTask` 在 ZERO_FORCE↔运行模式下**每次切换都成对调用 Stop/Enable**（`chassis.c:426-447`，200 Hz）。若两处都重置，会在每 5 ms 反复清积分，控制器永远建立不起积分。
- **附带**：`PIDReset` 后建议补一次 `DWT_GetDeltaT(&pid->DWT_CNT)`，避免重置 `DWT_CNT` 后首个 `dt` 异常放大 D 项。
- **验收**：零力↔运行反复切换后，重新使能无速度突变；Ozone 观察 `Iout` 在 Stop 后归零。

### B.2 [x] F3 电机离线只记日志、回调每 10 ms 重复

- **位置**：`dji_motor.c:151-156`；`daemon.c:43-49`
- **问题**：离线仅 `LOGWARNING`，不清 `pid_ref`/不复位 PID → 反馈冻结后梯形积分持续累积至 `IntegralLimit`（M3508 为 3000、GM6020 角度环 1000），恢复瞬间释放；`temp_count==0` 后 `else if` **每拍重复回调**，无"已上报"标志 → 8 电机 × 100 Hz ≈ **800 条/秒**刷屏（底盘板实际 4 个 M3508 + 4 个 GM6020 都会注册 daemon）。
- **方案**：① `daemon.c` 加"已上报"标志（超时只报一次，喂狗后重新武装）；② `dji_motor.c` 离线回调里清 `pid_ref`（与 B.1 联动，防积分冻结累积）。
- **跨板影响**：⚠️ `daemon.c` 是**双板共享模块** → 云台板视觉 daemon 的重复回调行为同时改变（属修复，但需在双板阶段回归）。
- **验收**：拔插 CAN，离线日志只出现一次；恢复后无窜车。

### B.3 [x] F4 `total_angle` 首帧偏差整圈

- **位置**：`dji_motor.c:144-148,161-162`
- **问题**：`malloc`+`memset` → `last_ecd = 0`，首帧即比较；约 **50% 开机概率**（首帧 `ecd > 4096`）出现 `total_angle` 与 `angle_single_round` 之间 360° 的坐标系错位。
- **影响面（已复核）**：舵向环因 `ds - cur_single` 先作差**不受影响**，但**任何把 `total_angle` 当绝对角的消费者**（固定参考的 `ANGLE_LOOP`、云台板 `gimbal.c:145`）会拿到 −360° 的错误绝对角。
- **方案**：加「**首帧只做初始化**」守卫 —— 首帧仅记录 `last_ecd`，不计算圈数增量。
- **验收**：上电后用 Ozone 观察 `total_angle`，首帧不再出现 −360 偏移。

### B.4 [x] F6 首周期微分冲击（幅值需台架定案）

- **位置**：`controller.c:66,133`；`chassis.c:127`
- **问题**：`PIDInit` memset 后 `Last_Measure = 0`，首个周期 `Dout = Kd×(0−Measure)/dt`，GM6020 角度环 `Kd=1`、`Measure` 为多圈角 → 首拍 D 项大幅为负，被钳到 `-MaxOut = -3000`。
- **方案**：PID 首拍跳过 D 项（用首帧标志，或判 `dt`/`Last_Measure` 有效性）。
- **台架验证**：Ozone 观测首拍 `angle_PID.Output`。

## 3. 阶段 C：底盘板本地健壮性

### C.1 [x] F8 daemon 喂狗竞态（低危）

- **位置**：`daemon.h:18`；`daemon.c:26-29`
- **问题**：`uint16_t temp_count` 未 `volatile`，由 CAN ISR 写、100 Hz 任务读改写；**任务侧递减**才是非原子的那一步（`DaemonReload()` 本身是单次 32 位赋值，原子）。概率极低，后果为单帧误报。
- **方案**：`temp_count` 加 `volatile`；任务侧读-改-写加临界保护。
- **跨板影响**：⚠️ `daemon.c` 双板共享，同 B.2。

### C.2 [x] 可选：P2 本地项（顺手改，与双板无关）

- **R31** `chassis.c:270-288`：`Normalize180/360` 的 `while` 归一化对 `±Inf` 会**死循环** → 改为有限次迭代或加 `isfinite` 前置判断。
- **R32** `bsp_dwt.c:91`：`CYCCNT64` 用 `UINT32_MAX`，应为 `2^32`（影响极小，但属明显笔误）。

### C.3 [ ] 可选：S1 健壮性（帧头重校验 + 帧间超时）
