## 2. P0 严重缺陷（S1-S6）

### S1. 板间 CAN 接收状态机无法重同步 —— ⚠️ **部分成立，降级为 P2**

- **位置**：`modules/can_comm/can_comm.c:26-71`
- **原文指控（不成立部分）**：`Chassis_Ctrl_Cmd_s` 为 21 字节、缓冲 25 字节、分帧 8+8+9，故首帧丢失后 `cur_recv_len` 依次为 8/16/24/32，"8 的倍数 ≡ 1 mod 9"，**永远无法收满也永不超界 → 永久卡死 → 底盘零力约 1 秒**。
- **修正后的数值**：命令结构体 = 4×float(16) + `chassis_mode_e`(4) + `int`(4) = **24 B**（`robot_def.h:165-177`，在 `:74` `pack(1)` 内）；`recv_buf_len = 24 + CAN_COMM_OFFSET_BYTES(4) = 28`（`can_comm.c:86`）；分帧循环 `for (i = 0; i < send_buf_len; i += 8)`（`can_comm.c:116-118`）→ **8/8/8/4**。
- **为何不卡死**：`recv_state == 0` 时，帧头/长度不符的帧在 `can_comm.c:31-39` 直接 `return`（`:38`），**不 append**。`cur_recv_len` 只有两条出路：`:44`（超界 → ResetRx）与 `:55-68`（恰好收满 → 无论 tail/CRC 成败都 ResetRx）→ **不可能无限累积**。

  | 场景 | 状态转移 | 结果 |
  | --- | --- | --- |
  | 丢第 1 帧 | 帧 2/3/4 在 `recv_state==0` 下被 `:31-39` 丢弃 | 本包全丢，下一包第 1 帧到达即重同步 |
  | 丢第 2 帧 | 帧 1,3,4 累计 20B；下一包帧 1 → 28B → `:58` tail 命中、`:60` CRC 失败 → `:67` ResetRx | 2 包作废（200 Hz 下约 **10 ms** 旧指令）后恢复 |
  | 丢第 4 帧（4B 尾帧） | 帧 1,2,3 累计 24B；下一包帧 1 触发 `:44` 超限 ResetRx | 同上 |
  | 外来巧合帧恰为 `'s',24` | 误置 `recv_state=1` 污染当包 | tail+CRC 拦截，一包内自愈 |

- **"1 秒零力"的真实条件**：零力入口是 `chassis.c:414-422`，其条件是 `CANCommIsOnline()` 为假，即 `daemon.c:33` `temp_count == 0` **持续成立**——需**连续约 1 s 无任何有效整包**（`daemon.c:17` 默认 reload=100 @100 Hz）。单帧丢失后下一包即 `DaemonReload`（`can_comm.c:64`）。
- **最终裁定**：✅ 降级为 **P2 健壮性缺陷**。真实成立的三点：① `recv_state == 1` 期间（`:41-70`）**不再校验帧头**，外来帧会污染当前包；② **无帧间超时**；③ `CANCommResetRx`（`:13-19`）只清 `cur_recv_len` 字节，无谓开销。
- **建议**：加「帧头重校验 + 帧间超时」；不改协议。

### S2. Bus-Off 无恢复 —— ✅ **成立（P0）**

- **位置**：`Src/can.c:48,80`；`bsp/can/bsp_can.c:53-58,115-127`
- **证据**：`can.c:48`（CAN1）与 `:80`（CAN2）均为 `AutoBusOff = DISABLE`，`:50/:82` `AutoRetransmission = ENABLE`；全树 grep **无** `HAL_CAN_GetError` / `HAL_CAN_ResetError` / 重新 `HAL_CAN_Start()`；`bsp_can.c:54-58` 只激活 RX FIFO 通知，**未启用错误中断**；`CANTransmit` 失败仅 `LOGWARNING` 后 `return 0`（`:115-117,124-126`），而全部调用方（`dji_motor.c:313`、`power_control.c:333`、`can_comm.c:121`、`super_cap.c:38`）**均忽略返回值**。
- **后果**：进入 Bus-Off 后上报与恢复双缺失，电机保持最后指令或滑行，上层毫不知情。
- **独立复核（pass B）补充两条重要精度**：① `HAL_CAN_Start()` 只执行一次是**来自 `if (!idx)` 守卫**（`bsp_can.c:65-69`），而非设计意图；② **即便主动重新调用 `HAL_CAN_Start()` 也无法恢复**——HAL 内部要求 `hcan->State == HAL_CAN_STATE_READY`，而进入 Bus-Off 后状态停在 `HAL_CAN_STATE_LISTENING` 且无人复位（`stm32f4xx_hal_can.c:1032-1039,1069-1073`）。③ 全部 10 个 `CANTransmit` 调用点都为裸语句丢弃返回值（`dji_motor.c:313`、`power_control.c:333`、`can_comm.c:121`、`super_cap.c:38`、`dmmotor.c:32,271`、`LK9025.c:149`、`HT04.c:26,98,200`）。④ 唯一的离线反应是打日志（`dji_motor.c:151-156`），**不存在 MCU 复位救援路径**。
  → 修复方案不能只是"重调 `HAL_CAN_Start()`"，需 `HAL_CAN_Stop()` → 复位状态 → `HAL_CAN_Start()` 的完整序列，或开 `AutoBusOff`。
- **裁定**：✅ 成立（P0）。**需台架**：人为制造 Bus-Off 验证。
- **决策点**：开 `AutoBusOff = ENABLE`（最简）还是显式检测错误后重 `HAL_CAN_Start()`？

### S3. `CANTransmit()` 超时单位为毫秒，会拖垮 1 kHz 任务 —— ⚠️ **部分成立，维持不降级**

- **位置**：`bsp/can/bsp_can.c:106-119`
- **成立部分**：`bsp_can.h:63` 明确 timeout 单位 ms；忙等循环（`:111`）；`DWT_GetTimeline_ms` 为 float（`bsp_dwt.c:109-116`）；返回值被所有调用方忽略。
- **修正后的数值（本轮重算）**：底盘板实际启用 **4 个**发送组 `[0][1][3][4]`——M3508 tx_id 1/3 → 组 1/4；GM6020 舵向拨码 ID 为 **2/4**（`chassis.c:155,157,161,163`）→ `motor_id = 1/3`，两者均 `< 4` → 取 `dji_motor.c:82-85` 的 `motor_id < 4` 分支 → 组 0（hcan1）/ 组 3（hcan2）。**组 2/5（0x2FF）不会置位**。
  → `DJIMotorControl()` 发送循环（`dji_motor.c:309-315`）最坏 **4 次 × 每次约 1 ms ＝ 约 4-8 ms** 阻塞，而 MotorTask 周期仅 **1 ms**（`robot_task.h:98`）。
- **报告中此前的错误**：正文"6 次"与核验块"4 组故应降级"都不准；正确说法是**4 组，但最坏仍达 4-8 ms，必须修**。
- **另注**：`CANCommSend()` 在底盘板发 `Chassis_Upload_Data_s` = 9 B（`robot_def.h:221-223`）＋4 = 13 B → **2 帧**（非"21 B / 3 帧"）。
- **裁定**：⚠️ 部分成立，**维持 P0/P1 不降级**（阻塞量级远超任务周期）。
- **决策点**：超时改 µs，还是改「非阻塞发送 + 失败计数」？

### S5. CAN 接收滤波器结构体未初始化 —— ✅ **成立（P0）**

- **位置**：`bsp/can/bsp_can.c:31-42`
- **证据**：`:31` `CAN_FilterTypeDef can_filter_conf;` 为未初始化局部变量，仅设置 `:34-40` 的 Mode/Scale/FIFO/SlaveStart/IdLow/Bank/Activation（`FilterIdHigh/FilterMaskIdHigh/FilterMaskIdLow` 均为 `uint32_t`，见 `stm32f4xx_hal_can.h:103-116`）→ 三者保持**栈垃圾**。在 `CAN_FILTERMODE_IDLIST` + `CAN_FILTERSCALE_16BIT` 下 `FilterIdHigh` 是**同一 bank 的第二个接受 ID**（`:38` STDID 左移 5 位布局正确）→ **非确定性地多放行若干 ID**。软件侧 `:158` 的 `rx_id` 比对可兜底不串数据，但浪费中断时间且极难复现。另 `HAL_CAN_ConfigFilter` 返回值被忽略（`:42`）。
- **独立复核（pass B）补齐底层机理与后果边界**：① HAL 在 `FilterScale = CAN_FILTERSCALE_16BIT` 下组装 `FR1 = (FilterMaskIdLow<<16)|FilterIdLow`、`FR2 = (FilterMaskIdHigh<<16)|FilterIdHigh`（`stm32f4xx_hal_can.c:916-932`）；在 `IDLIST` 模式下置 `FM1R`（`:956-960`）→ **16 位列表模式下一个 bank 的 4 个 ID 槽里，只有 `FR1[15:0]`（= `rx_id<<5`）是预期的，另外 3 槽是栈垃圾**。② 无人拦截：`assert_param` 被编译掉（`Inc/stm32f4xx_hal_conf.h:201,483` 未启用 `USE_FULL_ASSERT`）。③ 后果有界：多放行的垃圾 ID 只造成**多余的中断与 FIFO 占用**，`bsp_can.c:156-168` 会丢弃任何 `(handle, StdId)` 不匹配的帧，**不会解析出错误数据**。④ 垃圾值是否恰好命中某个真实 ID 取决于栈内容，**静态不可确定**——本报告只断言"未初始化读 + 寄存器写入 + 返回值被忽略"这三件事实。
- **裁定**：✅ 成立（P0）。修复：`CAN_FilterTypeDef can_filter_conf = {0};` 或 `memset`，并检查 `HAL_CAN_ConfigFilter` 返回值。

## 5. 已核实**不是**问题（避免误改）

1. ✅ **无 CAN ID 冲突**：`hcan1` tx `0x311`/rx `0x312`（`chassis.c:207-209`）；电机发送 `0x1FF`/`0x200`/`0x2FF`，反馈 `0x200+id`（M3508）/`0x204+id`（GM6020）互不重叠；过滤器 16 位 IDLIST、ID 左移 5 位正确。

3. ✅ **CAN 中断对 FreeRTOS 安全**：IRQ 优先级 5（`can.c:125-128,158-161`）= `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY`（`FreeRTOSConfig.h:111`）；回调内仅 `DaemonReload`/`DWT_GetDeltaT`/`memcpy`，不调用 FreeRTOS API。
4. ✅ **FIFO 不会丢帧**：`bsp_can.c:166` 的 `return` 只退出内层 `for`，外层 `while (HAL_CAN_GetRxFifoFillLevel(...))`（`:153`）继续取包。
5. ✅ **`steering_dirt[]` 无竞态**：写出与读取同链同任务（`chassis.c:369` 先解算舵向并更新 `steering_dirt` → `:370` 再解算轮速）。
6. ✅ **`rx_id` 与帧槽映射无 off-by-one**：M3508 1-4 → `0x200` 槽 0-3；GM6020 1-4 → `0x1FF` 槽 0-3。
7. ✅ **编码器多圈回绕判据正确**：`dji_motor.c:144-147` 中 `uint16_t` 相减提升为 `int`，`>4096`/`<-4096` 对 0↔8191 回绕符号正确（**不是**无符号回绕 bug）。
8. ✅ **`controller.c:32` 的 `CoefA` 除零不可达**：进入该分支蕴含 `CoefA > 0`。
9. ✅ **`bsp_init.h` 并非缺失**：header-only，`application/robot.c:1` 包含。

**另三条疑点排除**：

## 11. 验证方式

本环境**无工具链、无硬件 → 未编译、未上板**，上述结论均为静态分析。修复后建议：

- **静态**：确认无新增 `%f`/`%d` 取地址、无未判空 `malloc`、任务路径中无 `while(1)`。
- **台架**：用 Ozone 观察 `busy_count`、丢帧计数、`temp_count`；人为拔插 CAN 验证 Bus-Off 恢复；推车核对里程计速度；观测首个周期 `angle_PID.Output`（F6）；确认 O2 的跟随转向方向；在"无 USB host 枚举"条件下验证 R33 是否 HardFault。
- **实车**：功率不超限、无"莫名停顿"、云台板收到的回传值正确、`CHASSIS_FOLLOW_GIMBAL_YAW` 回正方向正确。

**仍需台架/实车才能定案的项**：O2（转向方向）、F6（微分冲击幅值）、R29（PID 整定）、S1（现场丢帧率）、R33（USB 解引用）、N2（换芯片行为）、D4（颜色语义）。
