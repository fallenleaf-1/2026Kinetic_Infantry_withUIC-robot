## 3. 新增发现（权威报告未收录，pass C 复核后按活跃度排序）

### 3.1 [P2] power_control.c 的 while(1) 未按 A.7 新模式升级
- **位置**：`power_control.c:92-95`、`:121-124`、`:129-130`（pass C 已逐处核实上下文）
- **事实**：两处 ID 冲突块均为「LOGERROR 一次（:92/:121，无 `BSP_FaultCode=1`）→ `while(1)` 内**每圈反复** LOGERROR」；:129-130 default 分支同样 `while(1) LOGERROR` 无 FaultCode。与 dji_motor.c/bsp_can.c 已统一的模式不一致，违反编码规则 3/14。日志标签还是复制粘贴来的 `[dji_motor]`。:94/:123 行尾注释含乱码 `(1!5!,LTC! (((不是)`。
- **缓解**：`PowerControlInit()` 全树无调用（S4/D.4 暂缓中），运行时不可达。**建议随 D.4 接回时一并重写**。

### 3.2 [P2] ⭐ bsp_pwm.c `PWMRegister()` 双重缺陷 —— **底盘板活跃路径上的 G1/R4 双漏列**
- **位置**：`bsp/pwm/bsp_pwm.c:30-33`
- **事实**：
  1. `:30-32` 越界检查是裸 `while (1) ;`（无日志、无 FaultCode）——G1 清单只统计了 iic/spi/usart 三个文件，**bsp_pwm 漏列**；
  2. `:32-33` `malloc` 后直接 `memset(pwm, 0, ...)` **未判空**——R4 清单同样漏列。
- **与 G1 其余 17 处的本质区别**：`PWMRegister` 是**底盘板固件当前唯一实际执行的 bsp 注册路径**（DaemonTask → `BuzzerInit()`（robot_task.h:106）→ `PWMRegister`）。G1 其余 17 处在底盘板上均无调用者；此处一旦触发（堆耗尽/超限注册）是**运行期裸死机**。
- **建议**：优先级高于 G1 其余项，修法与 A.5/A.7 一致（判空 + FaultCode + 单次日志）。

### 3.3 [P2·潜伏] LK9025.c 连续两次 malloc —— R7 同类未收录

### 3.4 [P2] R4 覆盖缺口全貌（pass C 全树清点）
- **全树自有代码共 25 处 `malloc`/分配调用点，仅 10 处判空**（已修的 7 处 + message_center 3 处）。未判空的 15 处分布：
  - **休眠路径 14 处**（当前底盘板无调用者）：bsp_gpio.c:32、bsp_iic.c:14(双重之一)、bsp_spi.c:15、bsp_usart.c:49、buzzer.c:30、ist8310.c:64、bmi088.c:414（经 `zmalloc`）、dmmotor.c:90,127、HT04.c:107、LK9025.c:55(双重之一)、servo_motor.c:16、super_cap.c:27、tfminiplus.c:9

### 3.5 [P2→建议升级关注] BuzzerTask 的 NULL 解引用在底盘板上每 10ms 实际发生
- **位置**：robot_task.h:106,113（`BuzzerInit()` + 每拍 `BuzzerTask()`）；buzzer.c:47-56 无 NULL 守卫。
- **事实**（pass C 已核实结构布局）：`BuzzzerInstance` 为自然对齐（float loudness 偏移 0-3、octave_e 4-7、**alarm_level 偏移 8-11**、alarm_state 12-15）。底盘板无人调用 `BuzzerRegister` → `buzzer_list[5]`（buzzer.c:8）全 NULL → 每拍读 `NULL->alarm_level` 即 **0x00000008（flash 别名区向量表第 2 项 NMI_Handler 指针）**，该值作为枚举比较恒为巨大值 > `ALARM_LEVEL_LOW` → 侥幸 `continue`。这条侥幸路径**当前每拍都在走**，编译布局一变（如向量表重定位）即 HardFault。一行判空即可消除。
- **附带**：N5 属实（buzzer.c:27 `> BUZZER_DEVICE_CNT` 应为 `>=`，传入 5 时 :38 `buzzer_list[5]` 越界写）；**N6 的机理经 pass C 复核存疑，见 §4.2**。

### 3.6 [文档纠错 + P3] CANFIFOxCallback 匹配即 `return` 退出整个函数
- **位置**：`bsp_can.c:216`（`if` 块内，非 for 循环之后）。
- **权威报告 §5.4 称**「return 只退出内层 for，外层 while 继续」——**表述错误**：C 语义中 `return` 直接返回函数，FIFO 中剩余帧本次中断不再取出。
- **实际后果有限**（pass C 复核维持）：bxCAN 的 FMP 挂起标志是电平型，ISR 返回后 FIFO 仍非空会立即重进中断，**不丢帧**；代价仅在多帧积压场景（中断被短暂屏蔽后）多几次中断进出，稳态低负载下无差异。属语义瑕疵 + 文档纠错，非功能 bug。

### 3.7 [P3] 零散项
- `.gitignore:51` `./idea` 为无效规则（`:57` 已有 `.idea/`），可删。
- `dji_motor.c:343-344` 注释「低八位/高八位」仍互换（`set >> 8` 实为高八位；R36 中代码注释部分未修）。

## 4. 对两份既有报告的纠错与存疑（pass C 新增裁定）

### 4.1 权威报告 §5.4（FIFO 不丢帧的理由）——理由错误，结论侥幸正确
见 §3.6。结论「FIFO 不会丢帧」仍成立，但成立机制是 FMP 电平重触发，不是「return 只退出内层 for」。

### 4.2 权威报告 N6（中间等级永不发声）——**机理与当前代码行为矛盾，建议改判**
- N6 原文：`buzzer.c:53` `if (buzz->alarm_level > ALARM_LEVEL_LOW) continue;` 配合 `ALARM_LEVEL_HIGH = 0` → 中间等级（1-3）永不发声。
- **pass C 实测**：`AlarmLevel_e` 为 HIGH=0 … LOW=4（buzzer.h:26-33），**`> ALARM_LEVEL_LOW(4)` 对全部合法枚举值（0-4）恒为假** → continue 永不触发 → 等级过滤完全失效。实际行为：从槽 0 起顺序扫描，第一个非 NULL 且 ALARM_ON 的实例**无论等级**都会发声（:90 break）。
- 即：真实缺陷与 N6 描述**方向相反**——不是「中间等级永不发声」，而是「优先级机制名存实亡，任何等级都可能抢先发声」（且 ALARM_OFF 的实例会先写一次占空比 0 再继续扫描）。
- **裁定建议**：N6 从「成立」改判为「机理描述错误，但该行确属语义缺陷（过滤条件恒假）」。修复时应按设计意图明确语义（如 `> 当前播报等级` 或显式优先级仲裁），而非照 N6 字面修。
