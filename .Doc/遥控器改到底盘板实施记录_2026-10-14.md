## 0. 摘要

按需求「把遥控器操控改到底盘板上控制」，采用**只挪遥控器接收**的方案：遥控器 DBUS 由**底盘板**接收并做离线保护，遥控器原始数据经 CAN **随底盘板既有上行帧**转发给云台板的 `robot_cmd`，由云台板照常解算云台/发射指令。

实现以**特性宏 `RC_RECEIVER_ON_CHASSIS`** 为开关，注释该宏即可零改动回退到原链路（遥控器接云台板）。改动集中在 3 个文件，`application` 层，未触碰 bsp 模块。

| `GIMBAL_BOARD` 编译  | **0 error**，RAM 78584 B / 59.95%，FLASH 113272 B / 10.80% |

## 1. 需求与选型

### 1.1 需求确认

与用户确认后确定的边界：

1. **改造范围** = 「只挪遥控器接收」：底盘板负责 DBUS 接收与离线保护，云台/底盘指令仍各自处理。
   - 不选「单板直控底盘」（方案 A 原案：底盘板内直接解算底盘平移/小陀螺）。
   - 不选「双板：底盘板当大脑」（会牵动视觉、弹道解算、双板通信方向重构，改动过大）。
2. **前置修复** = 「只做遥控器功能」：本次**不动 bsp 层**，方案文档《阶段 0 前置缺陷修复清单》中  
   `bsp_usart.c` / `bsp_pwm.c` / `buzzer.c` / `bsp_can.c` 的修复**本次未做**，仍为待办。

### 1.2 改动前现状（诊断）

- 当前工程定义 `CHASSIS_BOARD`（底盘板）。遥控器 `RemoteControlInit(&huart3)` **只在 `robot_cmd.c` 中调用**，  
  而 `robot_cmd.c` 的初始化与任务仅在 `ONE_BOARD` / `GIMBAL_BOARD` 下编译 —— **底盘板上遥控器从未接入**。
- 底盘指令的唯一来源是云台板经 CAN 下发（can1 `0x311` 下发 `Chassis_Ctrl_Cmd_s` / `0x312` 上传）。底盘板单板运行时必然恒为 `CHASSIS_ZERO_FORCE`。
- 安全缺陷 **RC-1**：`RemoteControlIsOnline()` 全工程零调用，断连后开关清零 → 指令冻结在最后值且**不急停**。
- `chassis_feedback_data` 在 `GIMBAL_BOARD` 构建下无引用，触发 `-Werror=unused-variable`，导致云台板配置**本来就编不过**。

## 2. 关键设计决策

### 2.1 复用既有上行链路，不新增 CAN 通道（重要）

底盘板→云台板本就有 `0x311 Chassis_Upload_Data_s` 上行链路，其载荷当前**几乎全为 0**。  
因此把遥控器数据**并入该帧**发送，而非新增 `0x313` 单向通道。

- **不改 CAN ID、不新增 CANComm 实例、不新增滤波器**；
- 避免新增一条「只发不收」的通道 —— 其守护进程在开机时必然因收不到数据而误报 lost。

> 早期草稿曾按 `0x313` 独立通道实现，后收敛为复用 `0x311`，最终代码不包含任何 `0x313`。

### 2.2 特性宏开关 + 冲突检查

`robot_def.h` 新增：

```c
/* 遥控器接收位置选择(仅双板有效)
 * 定义后: 遥控器(DBUS)接在【底盘板】USART3,由底盘板解析,并随底盘板上行帧
 *         (0x311 Chassis_Upload_Data_s,见RC_Data_s)转发给云台板的robot_cmd;
 *         robot_cmd.c 不再直接读取本板串口,并依据转发帧做遥控器/链路离线保护.
 * 注释后: 恢复原状 —— 遥控器接在云台板,由robot_cmd直接解析(原链路零改动).
 * 回退方式: 注释下面一行并重新编译两块板.
 */
#define RC_RECEIVER_ON_CHASSIS
```

并加编译期冲突检查（该宏依赖双板，单板无转发对象）：

```c
#if defined(RC_RECEIVER_ON_CHASSIS) && defined(ONE_BOARD)
#error RC_RECEIVER_ON_CHASSIS requires dual-board (CHASSIS_BOARD + GIMBAL_BOARD), not ONE_BOARD.
#endif
```

### 2.3 跨板数据结构

底盘板解析出的 `RC_ctrl_t` 无法跨板共享（其定义在 `remote_control.h` 且含位域 union），  
故在 `robot_def.h` 定义用于 CAN 传输的紧凑镜像 `RC_Data_s`（位于既有 `#pragma pack(1)` 区间内），  
并作为 `Chassis_Upload_Data_s` 的成员 `rc` 随上行帧发送。

覆盖字段：左右摇杆四轴、拨轮、左右开关、鼠标 x/y、按键位域 `key_press`、按键计数 `key_count[16]`、  
以及 `online`（底盘板 `RemoteControlIsOnline()` 结果）。

## 3. 改动清单（3 文件）

### 3.1 `application/robot_def.h`

- 新增宏 `RC_RECEIVER_ON_CHASSIS` 及冲突 `#error`。
- 新增 `RC_Data_s`（跨板遥控器镜像，`pack(1)`）。
- `Chassis_Upload_Data_s` 增加成员：
  ```c
  #ifdef RC_RECEIVER_ON_CHASSIS
      RC_Data_s rc; // 遥控器数据(接收在底盘板,随本上行帧一并转发给云台板的robot_cmd)
  #endif
  ```

### 3.2 `application/chassis/chassis.c`（发送端）

- `CHASSIS_BOARD` 下新增 `#include "remote_control.h"` 与静态 `rc_data` 指针。
- `ChassisInit()` 中注册遥控器（USART3 已按 DBUS 配置：100000 bps / Even / 9 bit + DMA）：
  ```c
  rc_data = RemoteControlInit(&huart3);
  if (rc_data == NULL) { LOGERROR(...); BSP_FaultCode = 1; while (1); } // 防御性判空
  ```
- `ChassisTask()` 内（200 Hz 任务）把遥控器各字段填入 `chassis_feedback_data.rc`，含 `online` 标志；  
  该填充位于 `CANCommSend(chasiss_can_comm, ...)` **之前**，随反馈帧一并上行。
- `chassis_feedback_data` 声明用 `#if defined(ONE_BOARD) || defined(CHASSIS_BOARD)` 包裹（见 3.4）。

### 3.3 `application/cmd/robot_cmd.c`（接收端）

- `GIMBAL_BOARD` 下新增本地镜像 `static RC_ctrl_t rc_remote_ctrl[2]`。
- `RobotCMDInit()`：定义 `RC_RECEIVER_ON_CHASSIS` 时**跳过本板串口注册**，并把 `rc_data` 指向本地镜像：
  ```c
  #if defined(RC_RECEIVER_ON_CHASSIS) && defined(GIMBAL_BOARD)
      // 遥控器已改接到底盘板,本板不再注册遥控器串口
  #else
      rc_data = RemoteControlInit(&huart3);
  #endif
  ...
  #ifdef RC_RECEIVER_ON_CHASSIS
      rc_data = rc_remote_ctrl;
  #endif
  ```
- 新增 `RCForwardToCtrl()`：把上行帧 `chassis_fetch_data.rc` 映射回 `RC_ctrl_t` 镜像。
- `RobotCMDTask()`：取到上行帧后，**仅当转发链路在线且遥控器在线**才刷新镜像，否则 `memset` 清零。
- `EmergencyHandler()`：增加离线急停判定（修复 RC-1）：
  ```c
  if (!CANCommIsOnline(cmd_can_comm) || !chassis_fetch_data.rc.online ||
      switch_is_up(rc_data[TEMP].rc.switch_left) || robot_state == ROBOT_STOP)
  ```

### 3.4 顺带修复

`chassis_feedback_data` 仅 `ONE_BOARD` / `CHASSIS_BOARD` 构建会发布或发送，用条件编译包裹后，  
`GIMBAL_BOARD` 配置不再触发 `-Werror=unused-variable`（此前云台板配置本来就编不过）。

## 4. 数据流（改造后）

```
[遥控器 DBUS] --USART3--> [底盘板 chassis.c]
                              │ 解析 RC_ctrl_t；RemoteControlIsOnline()
                              ▼
                 chassis_feedback_data.rc  ← 填充(200Hz)
                              │
                              ▼ CAN1  0x311 Chassis_Upload_Data_s（复用既有上行帧）
                        [云台板 robot_cmd.c]
                              │ CANCommIsOnline? 且 rc.online?  → 否则镜像清零
                              ▼ RCForwardToCtrl()
                       rc_remote_ctrl[TEMP]  (= rc_data)
                              │
                              ▼ 照常解算 Gimbal_Ctrl_Cmd_s / Shoot_Cmd_s
                        云台 / 发射机构
```

底盘板 → 云台板既有链路：`0x311`（上行反馈，含遥控器）、`0x312`（下行底盘指令）。  
本次**未新增任何 CAN ID**。

## 9. 追加：单底盘板直控（`CHASSIS_RC_DIRECT`）实施记录

### 9.1 背景与结论（为什么换路线）

现场**只有底盘板**，没有云台板。此时 §1–§8 的"只挪遥控器接收 + 转发给云台板"路线没有接收对象，
症状表现为**"遥控器接到底盘板却没反应"**。诊断结论：

1. **DBUS 接收本身没问题**：`RemoteControlInit(&huart3)` 已在底盘板（`chassis.c`），
   USART3 参数（100000 bps / Even / 9 bit / PC11 / DMA1_Stream1 + USART3+DMA IRQ）与 ioc 一致，
   静态核对无缺陷；底盘板只注册 1 个 USART 实例，不会触发 `DEVICE_USART_CNT` 停机。
2. **真正原因是"数据无人消费"**：§3.2 只把遥控器数据**填进 `0x311` 上行帧**，
   而 `ChassisTask()` 的指令来源仍然只有 `CANCommIsOnline/CANCommGet`。
   单板无对端 → `CANCommIsOnline` 恒 0 → 恒 `CHASSIS_ZERO_FORCE` → 怎么拨都不动。
3. **单板下继续发 `0x311` 还有额外危害**：CAN1 上无对端 ACK，且
   `Src/can.c` 中 `AutoRetransmission = ENABLE`，发送邮箱会被长期占满，
   使 CAN1 上的前轮 M3508 与舵向 GM6020 指令不可靠。

因此改用 2026-10-08 方案中的**方案 A**：`CHASSIS_RC_DIRECT` —— 遥控器仍接底盘板，
但由底盘板**自己解算底盘指令**，并且**不初始化 CANComm、不发送 `0x311`**。

### 9.3 映射与安全优先级（`RCDirectSet()`）

每周期先 `memset` 清空 `chassis_cmd_recv`，再按优先级填：

| 优先级 | 条件 | 结果 |
| --- | --- | --- |
| ① | `!RemoteControlIsOnline()`（100 ms 判离线） | `CHASSIS_ZERO_FORCE`（修复 RC-1：断连即零力，不看开关） |
| ② | 左开关 `switch_left` = [上] | `CHASSIS_ZERO_FORCE`（软急停，语义同原 `EmergencyHandler`） |
| ③ | 右开关 `switch_right` = [上] | `CHASSIS_ROTATE`（`ChassisTask` 内 `wz=25`） |
| ③ | 右开关 = [中] / [下] | `CHASSIS_NO_FOLLOW`（无云台编码器，`FOLLOW_GIMBAL_YAW` 降级；`wz=0`） |
| ③ | 右开关 = 0 或非法值 | `CHASSIS_ZERO_FORCE`（兜底：含断连清零后的 0、daemon 1 s 宽限期内无帧） |
| ④ | 右摇杆 → `vx/vy` | `±660` 量纲、`CHASSIS_DEAD_BAND(10)` 死区、`× CHASSIS_RC_SPEED_SCALE`；`offset_angle = 0`；`wz` 留给 `ChassisTask` 模式机 |

断连→零力最坏延迟 ≈ 100 ms（daemon）+ 5 ms（任务周期）≈ 105 ms。
上电 1 s 宽限期内即使没收过帧也是**零力**（开关值 0 落入 default），不会误动。

### 9.6 回退方式

1. **回退到双板路径**：注释 `robot_def.h` 中 `#define CHASSIS_RC_DIRECT`，重编译（`chassis.c` 原 CANComm 分支零改动）。
2. **启用双板转发路线**：先修**附录 A**，再注释 `CHASSIS_RC_DIRECT` 并打开 `RC_RECEIVER_ON_CHASSIS`，
   且两板必须同源编译烧录。
3. 任何异常：软急停（左开关[上]）→ 机械断电。

### 9.10 上电初始回正（"车的初始状态轮子朝正前方"）

**需求**：用户反馈"车的初始状态轮子的方向不是正前方"，要求改成初始即正前方。
经确认采用**只在上电初始阶段回正一次**的方案，之后沿用原逻辑（停车后保持上次行进方向）。

**机理诊断（三个独立原因，本次只处理第 1 个）**

| # | 原因 | 说明 | 本次处理 |
| --- | --- | --- | --- |
| 1 | 上电后未接管时是 `CHASSIS_ZERO_FORCE`，四路舵机**不带电** | `DJIMotorStop(servo_*)` → 舵轮停在断电前/任意角度，这就是"上电初始状态不正" | ✅ **本次修复**：上电主动回正 |
| 2 | 运动学里 `atan_angle[]` 只在有指令时更新（`chassis.c` 的 `if(!(vx==0&&vy==0&&wz==0))`） | 车停下后舵轮**保持刚才的行进方向**（斜向/横向），不回正 | ⏸ 按用户选择**保持原逻辑**（若日后要改：零指令时把 `atan_angle` 清零即可） |
| 3 | `±180°` 优劣弧翻转（`steering_dirt` 取反 + 目标 ∓180°） | 舵轮可能收敛到**反向**，视觉上不是正前方，但驱动方向被同步取反，行驶仍然正确 | ⏸ 运动时保留（保证走最短弧）；**回正阶段强制不翻转** |

**实现（`application/chassis/chassis.c`，均 `#ifdef CHASSIS_RC_DIRECT`）**

| 项 | 内容 |
| --- | --- |
| 新增宏 | `CHASSIS_ALIGN_TIMEOUT_MS 2000u`（回正阶段最长持续时间）、`CHASSIS_ALIGN_TOLERANCE_DEG 5.0f`（单轮到位容差） |
| 新增函数 | `RCDirectAlignServos()`：4 个驱动轮 `DJIMotorStop`（零输出，确保整车不动）；4 个舵向电机 `DJIMotorEnable` + 目标角 = `cur_total + Normalize180(标定正前方角 - cur_single)`，**不做 ±180° 翻转**，并把 `steering_dirt` 复正；返回"四轮是否都进容差" |
| `ChassisTask()` 顶部 | 一次性 `static uint8_t align_done` 阶段：每周期调用 `RCDirectAlignServos()` 并 `return`；四轮全部进容差**或**超时 2 s 后置位 `align_done`，交回 `RCDirectSet()` 正常流程 |
| 顺带整理 | 把运动学函数里的字面量 `base_dir[4] = {1,-1,1,-1}` 提为文件级 `static const int8_t SERVO_BASE_DIR[4]`，回正与运动学共用，避免两处字面量不同步（行为不变） |

**行为**：上电 → 驱动轮始终零输出，四个舵轮转向**标定的正前方**（最多自转 180°）→ 全部进入 5° 容差或 2 s 超时 → 交回正常遥控流程（其后停车不再自动回正）。

**日志**（RTT）：

```
I:[chassis] servo align done, LF/RF/LB/RB x10 = 1926 2263 465 1339     ← 已对准
W:[chassis] servo align timeout, wheels may not face forward            ← 2s 未到位(卡住/无反馈)
```

日志里的四个数 = 各轮当前 `angle_single_round × 10`，期望值即 `GM6020_*_ANGLE × 10`：
**LF 1926 / RF 2263 / LB 465 / RB 1339**（`robot_def.h`）。一致 → 软件侧回正到位。

**若回正后视觉上仍不正前方**：说明 `GM6020_*_ANGLE` 标定值与当前机械装配不符（软件无法自行判断"物理正前方"）。
重新标定步骤（每轮一次，需要 Ozone/RTT + J-Link）：

1. 不要上电驱动（保持 `ZERO_FORCE`），**手动**把该舵轮摆到正前方（轮面与车体纵轴平行）；
2. 读该 GM6020 的 `measure.angle_single_round`（即 `ecd × 360/8192`，或用本文 §9.9 的 J-Link 读取脚本）；
3. 把读数写入 `robot_def.h` 对应的 `GM6020_LF/RF/LB/RB_ANGLE`；
4. 四轮都标定后重编译烧录，重新上电复核 `[chassis] servo align done` 的四个数值与视觉朝向。

**验证步骤（需 J-Link 重连后执行）**

| # | 操作 | 通过标准 |
| --- | --- | --- |
| V5-1 | 上电（建议先架空/确认舵轮可自由转动），观察四个舵轮 | 四轮都转向并停在车头方向；驱动轮不转、车不位移 |

| V5-3 | 上电后立即推摇杆 | 回正阶段（≤2 s）内不响应摇杆属预期；回到正常流程后响应正常 |

| 项 | 说明 |

### 9.10.1 上机实测（2026-10-14 夜，J-Link 实测）

首次上机时"回正没生效"，追查后发现**真正的拦路石不是舵轮逻辑，而是整个固件根本没启动完**（见 §9.11）。
修掉 IMU 阻塞后，回正按预期工作，逐轮实测：

| 轮 | 实测单圈角 | 标定正前方 | 残差 | 判定 |
| --- | --- | --- | --- | --- |
| LF | 192.04 | 192.69 | +0.65° | ✅ |
| RF | 226.49 | 226.36 | −0.13° | ✅ |
| LB | 46.85 | 46.53 | −0.32° | ✅ |
| RB | 130.82 | 133.98 | **+3.20°** | ✅（在 5° 容差内） |

- 复位后 **0.5 s 内**四轮全部进入容差，日志：`I:[chassis] servo align done, LF/RF/LB/RB x10 = ...`。
- **RB 明显比其它三轮慢**：一次实测中 RB 从 18.8° 收到 4.65° 用了约 4.5 s（指数收敛、期间还有一次跳变），

### 9.11 启动被 IMU 零飘标定卡死（本次上机暴露的**更严重问题**，已修）

**现象**：烧录后固件"毫无反应"——没有 `[bsp_can] CAN Service Init` 日志、电机/舵轮从未初始化
（`servo_lf == NULL`）、`[rc] remote control lost` 也不出；J-Link 读回显示 20 个 `MX_*_Init`
全部完成、`SystemCoreClock=168MHz`、`_SEGGER_RTT` 已建立，但 `uwTick` 停在 **2 ms**、
`rc_init_flag=0`、RTT 一条日志都没有；故障寄存器 `CFSR/HFSR=0`（无 HardFault/Lockup）。

**定位过程（全部用 J-Link 读寄存器/内存完成）**

| 步骤 | 结论 |
| --- | --- |
| `uwTick == 2` + 全部 MX 外设已初始化 | 卡在 `RobotInit()` 的 `__disable_irq()` 区间内（HAL tick 被屏蔽，符合现象）|
| `DWT_CYCCNT` 50 ms 内推进 8 520 444（≈168 MHz×0.05 s）| **CPU 在执行**，DWT 正常，不是 Lockup/死机 |
| `hspi1.State = READY`、`SPI1 SR` 无 BSY | 不是卡在 SPI 传输 |
| `BMI088Driver` 的 `error=0x00`、`Accel 范数≈9.6`、陀螺零飘很小、`gNormDiff=0.19`、`gyroDiff≤0.09` | **传感器是好的**，初始化也成功 |
| `BMI088.gNorm = 41975`（未除以 6000 的累加值）、`caliCount` 停在标定循环内 | 卡在 `Calibrate_MPU_Offset()` 的"静止判定"do-while 里出不来 |

**根因**：`modules/imu/BMI088driver.c` 的 `Calibrate_MPU_Offset()` 只有一个 **12 s 时间兜底**，
且它依赖 `DWT_GetTimeline_s()`；本板上该兜底未生效（实测始终未打出 `[BMI088] Calibrate Failed`），
于是标定循环可以无限跑；而 `ins_task.c` 的 `while (BMI088Init(...) != BMI088_NO_ERROR);` 又是
**无日志、无上限**的外层重试。两者叠加 = 整个 `RobotInit()` 静默停死，电机/舵轮全部没初始化，
遥控器与回正自然全无反应（现场表现为"初始舵轮方向不一致"，因为舵机从未被指令过）。

**修复（两层）**

1. `BMI088driver.c: Calibrate_MPU_Offset()`：在 12 s 时间兜底之外增加**重试次数硬上限**
   `BMI088_CALI_MAX_TRYOUT`（5 次），超限即用离线参数并 `LOGERROR`，杜绝无限循环。
2. `ins_task.c: INS_Init()`：
   - 重试改为**有上限**（`INS_INIT_TIMEOUT_MS 3000`），超时 `LOGERROR + BSP_FaultCode=1`；
   - **单板直控跳过零飘标定**（`BMI088Init(&hspi1, 0)`）：本模式不使用姿态（仅跟随模式需要 IMU），
     标定既慢又可能不收敛，跳过它保证舵轮能尽快初始化与回正（代价仅 IMU 零飘未标定）；
   - 其它构建（`GIMBAL_BOARD`/`ONE_BOARD`）保持原语义：`gimbal.c` 会解引用 IMU 指针，不能返回 NULL，
     故超时后仍是"响亮停机"，但改为**有日志、有次数上限**，不再静默。
3. `INS_Task()` 增加 `IMU_Available` 守卫：IMU 未初始化成功时不读传感器（避免用死数据做解算）。

**验证**：烧录后启动日志完整（`[bsp_can] CAN Service Init` → 各任务 → `[rc] remote control lost`），
回正随即可执行（见 §9.10.1）；三构型（`CHASSIS_BOARD`/`GIMBAL_BOARD`/`ONE_BOARD`）`-Werror` 0 warning。

**遗留**：`Calibrate_MPU_Offset()` 的 12 s 时间兜底为何未生效尚未定论（疑与 `DWT_GetTimeline_s()`
在该阶段的表现有关）；现已由次数上限兜住，但建议后续单独复查该函数的时间判定。
`modules/BMI088/bmi088.c`（另一套未启用的实现）内有两个 `while(1)` 未判长度，属同类隐患，登记待清理。

#### 9.13.2 顺带定位并修掉"舵轮完全没力矩"（NaN 锁死，F8）

排查"上电回正为什么不动"时发现四个舵轮**全都没有力矩**：角度环输出饱和（`a_out = ±3000`）却完全不转。
J-Link 读 PID 内部（`servodiag`）：

```
LF stop=1(ENABLED) | a_ref=133.40 a_meas=133.37 a_out=0.98
   spdPID dt=0.00106 err=3000 Dout=0 Iout=nan ITerm=0.318 Kd=0
```

- **根因**：`PIDCalculate()` 的 `Iout += ITerm` 一旦累加进非有限值，**NaN 会永久留在 `Iout`**；
  死区分支只清 `Output`/`ITerm`、**不清 `Iout`** ⇒ `Output = Pout + Iout + Dout` 恒为 NaN
  ⇒ `(int16_t)NaN` 取 0（未定义行为）⇒ 电调恒收 0 电流 ⇒ **该电机此后永远没有力矩**（要复位才恢复）。
- **NaN 来源**：微分项/输出滤波都是**除以 `pid->dt`**（`controller.c:173`、`f_Derivative_On_Measurement:66`、
  `f_Output_Filter:79`），`dt == 0` 时立刻产生 inf/NaN。
- **修复**（共享代码，三构型同时生效；只增加保护，有限值路径行为不变）：
  1. `controller.c`：`dt` 非有限或 ≤0 时按 1 ms 处理；每拍开头检测 `Iout/Dout/Last_Err/Last_Measure`
     非有限则清零重起算；`measure`/`ref` 非有限时直接返回 0 并清状态；返回前兜底 `isfinite(Output)`。
  2. `dji_motor.c`：`set = (int16_t)pid_ref` 之前，非有限值按 0 处理并限幅到 int16 范围（补 `#include "math.h"`）。
- **修复前后物理验证（决定性）**：把 `GM6020_LF_ANGLE` 临时改成 153.40（+20°）→ 上电后 LF 编码器角
  从 133.42° 自己转到 **152.66°**（约 19.3°，1 s 内到位）→ 改回 133.40 后又转回 **134.03°**。
  证明"标定角 → 上电回正 → 舵轮物理转动"整条链路是通的（修复前四个舵轮一动不动）。
- 编译：三构型 0 error/0 warning（CHASSIS FLASH 104724 B、GIMBAL 114424 B、ONE 117692 B）；
  烧录回读 PASS（`0x08000000..0x08019913`），最终映像 MD5 `B007BCE804FE82F0CC593ED26DBEE0DB`。

### 9.15 后轮驱动方向取反（前/后轮对顶，"无法前进后退"，2026-10-15）

**现场现象**：推杆前进时**前轮滚动方向正确、后轮相反**，前后对顶导致整车无法前进后退。

**定位**：`steering_dirt` 的基准方向 `SERVO_BASE_DIR` 只按"左右镜像"假设取了 `{1,-1,1,-1}`（LF,RF,LB,RB），
而本车**前/后模组的驱动方向相反** → 后两个轮子要取反。与转向角标定无关（§9.13 的四轮标定值本身是对的）。

**改动**：`chassis.c` 的 `SERVO_BASE_DIR` 与 `steering_dirt` 初值 `{1,-1,1,-1}` → **`{1,-1,-1,1}`**：

| 轮 | 旧 | 新 |
| --- | --- | --- |
| LF | +1 | +1 |
| RF | −1 | −1 |
| LB | +1 | **−1** |
| RB | −1 | **+1** |

**为什么改驱动符号而不是改标定角**：某个舵轮若被装/摆在"正前方+180°"的方位，与"该轮驱动符号取反"对整车推力**完全等价**
（绕竖直轴转 180° 是舵轮模组的对称操作，麦轮/全向轮的滚子朝向也随之对称），所以改符号即可，
且不会让上电回正时轮子突然自转 180°。

**验证**：编译三构型 0 error/0 warning（CHASSIS FLASH 108084 B，MD5 `1CE93DE61E63A0C8EB4A7CAD6F443BF6`），
烧录回读 PASS（`0x08000000..0x0801A633`）；复位后 J-Link 读到 `steering_dirt=[1,-1,-1,1]` ✓，
四轮仍在标定正前方（残差 ≤0.37°）。
**待现场**：架空四轮，推杆前/后/左/右，确认四轮滚动方向一致（前进时四轮下缘都向后滚）。

**附注（遥控器硬件）**：现场遥控器**左摇杆损坏、只有右摇杆可用** —— 不影响使用：
单板直控的速度指令只取右摇杆（前后=`rocker_r1`、左右=`rocker_r_`），示教模式只用左右拨杆 + 右摇杆。

### 9.18 现场"遥控器接云台板却打不动底盘"的定位（2026-10-15 晚，双板）

**现象**：`CHASSIS_BOARD`（双板、无 `CHASSIS_RC_DIRECT`）已烧录，接收机插云台板、遥控器开机，但推右摇杆底盘不动。

**逐层定位（J-Link 实测，每层都给出器件级证据）**

| 层 | 实测值 | 结论 |
| --- | --- | --- |
| 底盘板板间链路 | `chasiss_can_comm`：`recv_data_len=21 / recv_buf_len=25`、`cur_len=25`、`resync=0 / crc_err=0 / tail_err=0`、daemon `temp=100 → ONLINE` | 0x312 **正常**，底盘在忠实执行"零力" |
| 底盘板收到的指令 | `chassis_cmd_recv`：`mode=ZERO_FORCE / vx=vy=wz=0 / off=65.52 / speed_buff=40`；连续 **71 s** 采样**一个数都没变** | 车不动**与底盘无关** |
| 云台板遥控器模块 | `rc_init_flag=1`（`RemoteControlInit` 已执行）但 `rc_online=0`、daemon `temp=0 / reload=10 / reported=1`、`rc_ctrl` 全 0、RTT `W:[rc] remote control lost` | 云台板**一个 DBUS 帧都没收到** |
| 云台板 USART3 | `CR1=0x0000351C`（`UE=1 RE=1 9bit 偶校验 IDLEIE=1 DMAR=1`）、`BRR=0x1A4`（100 kbps 正确）、`DMA1_S1 CR=0x08000417 EN=1 NDTR=18 PAR=0x40004804`、`SR` 无 `ORE/FE/NE/PE` | 接收通道**配置与挂载完全正确**，只是**一个字节都没进来** |
| 云台板全部串口 | 被动扫 `USART1/2/3/6`、`UART4/5` 的 `SR`（有无 `RXNE/ORE`）与全部 DMA 流 `NDTR`：**全静**；RTT 里**没有** `[bsp_usart] USART error callback triggered` | 既不是"插错口"也不是"收到乱码" ⇒ **物理层完全没有信号**（接收机供电/线序/对频/接口反相器） |
| 接收机重新接好后 | `rc_online=1`、daemon `temp=9/10`、`switch_left/right` 读数正常、`robot_state=1(READY)` | 接好即恢复，进一步确认是物理连接层 |

**第二层原因（真正让用户"打不动"的）**：接收机通路恢复后，左侧开关仍在 **[中]** 档。原逻辑（`robot_cmd.c`）：

- 左**[上]** = 急停；左**[中]** = **键鼠控制**（`MouseKeySet()`：只读鼠标/键盘，**不读摇杆、也不设置 `chassis_mode`** ⇒ 底盘恒 `CHASSIS_ZERO_FORCE`）；
  左**[下]** = **遥控器控制**（`RemoteControlSet()`：按右开关给 `ROTATE / NO_FOLLOW / FOLLOW_GIMBAL_YAW`，并用右摇杆算 `vx/vy`）。
- 240 s 现场采样（`rcwatch`）三档对照：`swL=MID` 期间右摇杆推到 ±660，`mode` 恒 `ZERO_FORCE`、`vx/vy` 恒 0；
  `swL=DOWN` 期间 `mode=2(NO_FOLLOW)`；`swL=UP` 期间 `robot_state=0(急停)` —— 与代码逐条吻合。

**现场操作规程（务必按此操作）**

1. 上电前把**左开关放在[中]**（或上电后先过一遍[中]）：这是"解除急停/恢复运行"档，RTT 会打 `I:[CMD] reinstate, robot ready`；
2. 需要驾驶时打到**左[下] + 右[中]**（不跟随平移），再推**右摇杆**（前推=前进，满杆 = `660×25 = 16500 = CHASSIS_WHEEL_SPEED_MAX` 满量程）；
3. 左[中] 是键鼠模式，**此时右摇杆无效**（这是本次"打不动"的直接原因）；左[上] = 急停（`robot_state=0`、四轮零力、舵轮保持正前方）；
4. 遥控器未开机/掉线超过 100 ms（daemon `reload=10@100Hz`）也会进急停，必须先把左开关过一遍[中]才能恢复。

**顺带发现的安全隐患（待处理，未改代码）**：示教手势"左[下]+右[下] 保持 1.5 s"与**正常驾驶档 `右[下]=FOLLOW_GIMBAL_YAW` 完全重叠** ——
用跟随模式驾驶时只要保持 1.5 s 就会误入示教：四舵轮立刻断电（手可自由摆动）、四个驱动轮 `DJIMotorStop`，车会"突然失控"。
建议把云台板侧手势换成不与任何驾驶档重叠的组合（例如 **左[中]+右[下]**：键鼠模式下右开关不参与驾驶，左摇杆/右摇杆也不参与，安全且仍能用右摇杆前/后到底保存/恢复）。

**其它观察（无副作用，已核对）**：`chassis_speed_buff` 低 8 位被 `MouseKeySet()` 写成 `40`（C 键档位 default 分支）；
底盘侧只读**高 8 位**的示教命令（`SteerTeachCmd()`），低 8 位不参与任何解算，可忽略。

### 9.19 示教手势改造 + 示教"永久卡死"死锁修复（2026-10-15 夜，现场实测通过）

**背景**：§9.18 发现"进入示教 = 左[下]+右[下]"与正常驾驶档 `右[下]=FOLLOW_GIMBAL_YAW` 重叠（跟随模式开 1.5 s 就会误入示教，四舵轮突然失力）；现场实测保存不成功。

**(1) 手势改动（仅云台板 `robot_cmd.c SteerTeachCmdUpdate()`）**

| 项 | 原 | 现 |
| --- | --- | --- |
| 进入 | 左[下]+右[下] 1.5 s | **左[中]+右[下] 1.5 s** |
| 退出 | 左[上] 或遥控器离线 | **左开关离开[中]（含[上]急停）** 或遥控器离线 |
| 重复进入 | 按住不放会不断重入 | 手势必须**松开过一次**（`rearm`）才能再次进入，保存后按住不放不会自动重入 |

选 左[中] 的理由：左[中] 是键鼠档，该档下 `MouseKeySet()` 只读鼠标/键盘，**右开关与右摇杆都不参与驾驶**，因此手势期间车不可能被驱动，与任何驾驶状态都不冲突。

> **遗留（单板直控构型）**：`CHASSIS_RC_DIRECT` 下 `RCDirectSet()` 的映射是"只要左开关不是[上]就可驾驶"（左[中]/[下] × 右开关三档），
> 不存在"不参与驾驶"的开关组合，因此 `RCDirectTeachUpdate()` 的进入手势仍是 左[下]+右[下]（与"不跟随"驾驶档重叠）。
> 本机构型不用单板直控，暂不改；若日后切回单板直控，建议改用拨轮（`rc.dial`，该模式下完全未使用）做修饰键来避开冲突。

**(2) 保存动作判定加滞回**：原实现 `stick >= 600` 否则立即清零，实测"压到底保持 1 s"很容易因摇杆抖动/没压到机械极限被打断（两次尝试均失败）。
现改为 `STEER_TEACH_STICK_KEEP 450`（超过即累计）/`STEER_TEACH_STICK_RESET 300`（回到 ±300 内才清零），中间带维持方向继续累计。单板直控侧 `RCDirectTeachUpdate()` 同步改成同样的滞回。

**(3) 一次性命令改为"保持 + 边沿检测"**：SAVE/RESTORE 原先只在命中那一拍（5 ms）有效，而 0x312 是 200 Hz 四帧包，底盘任务采样相位与之不对齐时会整包不被读取 → 命令静默丢失。
云台板现在把该命令**保持 40 拍（200 ms）**下发（`STEER_TEACH_CMD_HOLD_TICKS`），底盘侧 `SteerTeachCmd()` 对 SAVE/RESTORE 做**边沿检测**（重复送达只执行一次，`ENTER` 仍每拍返回，否则示教期间舵轮会重新通电）。

**(4) 真正的根因：`ChassisTask` 提前 return 造成的示教死锁（严重）**
`ChassisTask()` 里"刷新指令"代码块原本在示教分支**之后**，而双板下 SAVE/RESTORE/退出示教这些命令**本身就是随 `chassis_cmd_recv` 送达的**：

```
进入示教(ENTER) → 示教分支每拍提前 return → 永远到不了刷新指令那一行
              → chassis_cmd_recv 冻结 → SAVE/RESTORE/NONE 永远收不到 → 永久卡在示教
```

现场证据（本次抓到的完整指纹）：底盘 `chassis_cmd_recv` 连续 60 s **一个字节都不变**（`buff=296/teach=1`、`off=76.52`）、
`CANCommInstance.update_flag` **恒为 1**（该位只由 `CANCommGet()` 清除 ⇒ 消费端没在跑这一行）、而 CANComm 守护进程
`temp_count=100` **ONLINE**（该守护只在**整包收齐**时喂狗 ⇒ 包其实一直在正常送达）。
后果不只是"保存失败"：**示教退出不了、示教结束后整车也无法驱动**（八电机恒零输出），只能复位。

修复：把"指令来源刷新"整块移到 `ChassisTask()` **最前面**（示教/回正分支之前），并加注释说明原因。
修复后实测 `update_flag=0`（消费恢复）、`chassis_cmd_recv` 随遥控器实时变化。

### 9.20 云台 IMU 姿态 NaN（大yaw/pitch 角度环反馈恒 NaN ⇒ 电机不动）+ 大yaw 反馈源改造（2026-10-15 深夜）

**现象**：想用左摇杆转大yaw，但 `gimbal_cmd_send.yaw` 正常变化、**大yaw 电机却完全没反应**（`speed_aps=0`）。

**(1) 根因：QuaternionEKF 的姿态输出永久 NaN（N1，严重）**

J-Link 实测（`gimbal_fetch_data` 与 INS 原始结构体一致）：

| 字段 | 值 |
| --- | --- |
| `Gyro[3]` / `Accel[3]` | −0.012/−0.033/0.017、−6.22/7.06/2.33 ✅ 正常 |
| `Roll / Pitch / Yaw / YawTotalAngle / BigYaw_Feed` | **全部 `nan`（0x7FC00000）** ❌ |
| `QEKF_INS` 内部 `IMU_QuaternionEKF`（状态/协方差，+4..+311） | 全有限（**没有** NaN） |
| `QEKF_INS.q[4]`(+336)、`GyroBias[0..1]`、`Gyro[0..1]`、`Accel[3]`、`OrientationCosine[3]`、`gyro_norm/accl_norm`、`Roll/Pitch/Yaw/YawTotalAngle`、`ChiSquare_Data`、`YawAngleLast` | 全 NaN ❌ |

`QEKF_INS` 里那 308 B 的 `KalmanFilter_t` 只存**指针**，真正的状态/协方差缓冲在 `pvPortMalloc` 的堆上（`kalman_filter.c:167...`）——所以"结构体内没有 NaN、镜像量全 NaN"并不矛盾。

**机理（代码级）**：`QuaternionEKF.c` 用四元数预测重力方向，再取方向余弦：

```c
QEKF_INS.OrientationCosine[i] = acosf(fabsf(kf->temp_vector_data[i]));   // 越界→NaN
...
kf->K_data[i * 3 + j] *= QEKF_INS.OrientationCosine[i - 4] / 1.5707963f; // NaN进入增益
...
xhat = xhat' + K·(z - h(xhat'))                                          // 状态被污染
```

`temp_vector_data[]` 由四元数算得，浮点误差会让 `|值|` 略大于 1 ⇒ **`acosf(1.0000001)=NaN`** ⇒ 增益 K 变 NaN ⇒ `xhat`/`FilteredValue` 永久 NaN；
而 `P` 因残留卡方检验走 `SkipEq5=TRUE`（跳过 P 更新）反而保持有限 —— 与实测完全吻合。
**一旦 NaN 就没有任何恢复机制**，云台 `BigYaw_Feed`（`yaw_motor` 的角度环反馈，`gimbal.c:52`）与 `Pitch`（DM 电机反馈）恒为 NaN，PID 输出恒 0 ⇒ 大yaw/pitch 电机永远没反应（需复位）。

**修复（共享模块，N1）**

| 文件 | 修复 |
| --- | --- |
| `QuaternionEKF.c` | ① `acosf` 参数夹紧到 `[0,1]`（`!(c<=1)` 同时覆盖 NaN）；② `invSqrt(x)` 在 `x<=0` 时返回 0；③ `dt` 非正/过大时用 1 ms；④ 新增 `IMU_QuaternionEKF_Reset()`：只重写已分配的 `xhat/P/FilteredValue` 等缓冲（**不能再调 `IMU_QuaternionEKF_Init`**，`Kalman_Filter_Init` 每次都 `pvPortMalloc`，反复调用会耗尽FreeRTOS堆），并用一份只读的初始 P 副本 `IMU_QuaternionEKF_P_init` |
| `ins_task.c` | ① `InitQuaternion()` 逐项防 NaN（加速度范数为 0、点积越界、加速度与重力平行导致叉乘≈0 → 退回单位四元数并打日志）；② `INS_Task()` 每拍检查 `QEKF_INS.q/Yaw/Pitch/Roll` 是否有限，非有限则**用当前加速度重建 EKF**（限频 1 s，因为 `InitQuaternion` 要读 100 次加速度≈100 ms），本拍直接返回以保留上一拍的有限值，不把 NaN 扩散给云台/视觉 |
| `user_lib.c` | `Norm3d()` 零模长/非有限时不做除法 |

**验证（烧录后实测）**

```
修复前: Roll/Pitch/Yaw/YawTotalAngle/BigYaw_Feed = nan / nan / nan / nan / nan
修复后: gyroZ=0.0049  Yaw=11.466  YawTotalAngle=11.466  BigYaw_Feed=308.666   ✅ 有限
```

（`BigYaw_Feed = YawTotal − (0 − 297.2°)`，那 297.2° 是**小yaw电机未接**时 `CalcSmallYawOffsetAngle()` 的固定偏置，`297.2° = 6763 × 0.043945` 与宏完全一致。）

**(2) 大yaw 反馈源改为电机自身编码器（现场要求）**

现场"只挂了大yaw电机"且要求不依赖 IMU 姿态，因此 `robot_def.h` 新增开关（默认注释=电机反馈）：

```c
// #define GIMBAL_YAW_FEEDBACK_IMU   // 定义=用IMU的BigYaw_Feed(设计原意,绝对指向); 注释=用大yaw自身编码器
```

`gimbal.c` 依据该宏选择 `DJIMotorChangeFeed(..., OTHER_FEED/MOTOR_FEED)` 与初始化配置。

**(3) "一切到左[下]就疯狂旋转"的根因：使能瞬间指令基准未对齐（严重）**

现场 45 s 采样（`yawwatch`）直接拍到：`swL=DOWN` 时 **`yaw_ref=225.04°`，而大yaw反馈只有 11.67°(IMU)/≈0°(电机)**。
原因：**停机期间（ZERO_FORCE/急停/遥控器离线）大yaw 电机是停的，但 `robot_cmd` 仍在按摇杆累积 `gimbal_cmd_send.yaw`**；一旦恢复 `GIMBAL_GYRO_MODE` 使能，参考与反馈之间就是几十~几百度的阶跃误差 ⇒ 角度环满输出（`MaxOut=1000`）冲过去。小yaw未接带来的 297° 固定偏置会进一步放大。

**(4) 大yaw 转速降低**：左摇杆水平→大yaw 的系数由 `0.0025`（满杆 ≈330°/s）降到 **`0.0009`（满杆 ≈119°/s）**，提为 `robot_def.h` 的宏 `GIMBAL_YAW_RC_SCALE`，三个档位分支共用，一处可调。

### 9.21 大yaw 控制环改造：位置环 → 速度环（2026-10-15 深夜，现场数据驱动）

**(1) 位置环为什么会"堵转 2s 后满速冲出去/明显振动"（实测证据）**

45 s + 50 Hz 采样（`yawdiag`）抓到位置环饱和状态：

```
angle=347.78  speed=-5.1  cur=132 | aErr=-347.781  aOut=-1000.00  aRef=0.00
                                   | sErr=-994.14   sOut=-20000.00 sIout=-0.26
```

- 停机期间（ZERO_FORCE/急停/遥控器离线）`yaw_motor` 是停的，但 `robot_cmd` 仍按摇杆累积 `gimbal_cmd_send.yaw`
  ⇒ 使能瞬间/hand 挡住轴时，位置误差会涨到几百度的量级；
- `angle_PID.MaxOut = 1000`（单位是**速度环的 RPM**）⇒ 位置环可以一次性要求 **1000 RPM = 6000°/s**，
  于是"堵转 → 误差累积 → 一脱开就满速冲出去、不可控"；
- `speed_PID.Ki=10` 在堵转期间还会积分（`IntegralLimit=3000`），脱开后进一步过冲；再加上高增益级联 ⇒ 明显振荡/顿挫。
- 该 yaw PID 参数**从未在硬件上验证过**（此前 yaw 因 IMU NaN 一直不动，见 §9.20），所以这是首次整定。

**(2) 改为速度环（默认）**

| 位置 | 改动 |
| --- | --- |
| `robot_def.h` | 新增 `ROBOT_TASK_HZ 200.0f`、`GIMBAL_YAW_SPEED_LIMIT 200.0f`(°/s 兜底限幅)、宏开关 `GIMBAL_YAW_POSITION_LOOP`（注释=速度环，默认；定义=原位置环）；`Gimbal_Ctrl_Cmd_s` 新增字段 **`float yaw_rate`**（°/s；该结构体只在云台板内经消息中心传递，不过 CAN，可自由扩展） |
| `robot_cmd.c` | 三个档位与 `MouseKeySet()` 都同时给出 `yaw_rate`（= `每拍角度增量 × 200Hz`），位置环字段 `yaw` 保留 |
| `gimbal.c` | yaw 配置按宏选环路：速度环 `outer/close_loop_type = SPEED_LOOP`（角度环不参与）；`GIMBAL_GYRO_MODE` 下把 `yaw_rate/6`（°/s→RPM，GM6020 直驱 1RPM=6°/s）作为速度参考并做 ±`GIMBAL_YAW_SPEED_LIMIT` 限幅；位置环分支保留（含 §9.20 的基准对齐） |

速度环的好处：**没有位置误差可累积**（堵转再久也只是速度误差），输出被参考限幅，不会出现"弹射"。
代价：松杆后不钉住角度（可被外力推动），只把转速压到 0。

**(3) 速度环首次实测：太弱（不是逻辑错）**

RC 正常（`l_` 到 ±660、`rate` 到 ±118.8°/s、满杆 118.8°/s = `0.0009×660×200` 与设计一致），但电机几乎不动：

```
t=39.14  ang=160.97 spd=0.0 | sErr=0.72→5.07  sOut=144→1030 | rate=5→30.4°/s | l_=-28→-169
```

- `sErr` 恰好等于指令值本身（`30.4°/s ÷ 6 = 5.07 RPM`）⇒ **实际转速恒为 0**；
- `sOut` 只有 144→1030（满量程 20000 的 **5%**，≈3% 电压 ≈0.06 N·m）⇒ 压不过云台轴静摩擦 ⇒ "只慢慢爬"；
- 原因：原 `Kp=200` 时 5 RPM 误差仅 ~1000 输出，而 `Ki=10` 的积分累积速率约 `10×5RPM×1ms×1000 ≈ 50/秒`，
  要 ~60 s 才能积到 `IntegralLimit=3000`；现场另被改成 `Kp=1`（几乎全靠积分）⇒ 更慢。

**整定后参数（已编译烧录，实测待补）**

```c
.speed_PID = { .Kp = 1000, .Ki = 400, .Kd = 0, .IntegralLimit = 8000, .MaxOut = 20000 }
```

（Kd 置 0：转速反馈有量化与 ~1ms 延迟，微分易放大成振动；角度环 `Kp=50` 在速度环模式下不参与。）

**固件**：`GIMBAL_BOARD` FLASH 117256 B，MD5 `E483AB56300CE336876F88F327D7A1F2` —— 已烧录 + 回读 PASS。

> **待验证/现场阻塞（2026-10-15 深夜）**：整定后复测时，采样到电机实例**全为 0**
> （`angle=0 / speed=0 / sErr=0 / sOut=0`，3415 个样本），说明**固件侧没收到该电机的 CAN 反馈**（电机未上电或 CAN 线未接），
> 且随后 J-Link 读 `0x2000831C` 超时（USB 枚举正常 ⇒ 目标板掉电或 SWD 排线松动）。

### 9.22 大yaw 速度环"自激"的根因：**速度反馈量纲是 deg/s 而不是 RPM**（2026-10-15 深夜，已修复验证）

**现象**：速度环无论怎么调都"要么不动、要么剧烈振荡"（`sOut` 在 ±20000 每 20 ms 翻转、`spd` 报 ±500°/s、
角度只摆 ±3.5° ⇒ 约 **100 Hz 极限环**；再把增益调小则"只慢慢爬"）。

**根因（量纲）**：驱动层 `dji_motor.c:144`：

```c
measure->speed_aps = (1 - SPEED_SMOOTH_COEF) * measure->speed_aps +
                     RPM_2_ANGLE_PER_SEC * SPEED_SMOOTH_COEF * (float)((int16_t)(rxbuff[2] << 8 | rxbuff[3]));
// general_def.h: #define RPM_2_ANGLE_PER_SEC 6.0f   // ×360°/60sec
```

`speed_aps` 的单位是 **deg/s**（= RPM × 6）。第一版按 `yaw_rate/6`（当作 RPM）下发、并把增益按 RPM 量纲取到 `Kp=300`——
在 °/s 量纲下等于把同一误差再放大 6×6=36 倍，必然饱和自激。底盘板同型号 GM6020 舵向电机的注释早已写明
"**角度环输出即速度环参考(deg/s)**，GM6020物理极限约1920°/s"，其实际取值就是 `speed_PID.Kp=10 / Ki=0.1`。

**修复**

| 项 | 修正 |
| --- | --- |
| 速度参考 | `yaw_spd_ref = gimbal_cmd_recv.yaw_rate`（°/s **直接给**，不再 ÷6）；限幅 `±GIMBAL_YAW_SPEED_LIMIT`（°/s） |
| 速度环增益 | `Kp=300 → 10`、`Ki=200 → 0.5`、`Kd=0`、`IntegralLimit=3000`、`MaxOut=20000`（对齐底盘板已验证参数） |
| 摩擦前馈 | 保留 `GIMBAL_YAW_FRICTION_FF=2500`（经 `current_feedforward_ptr` 直接叠加在速度环输出上），阈值改为 **°/s**（±3°/s） |

**实测（50 Hz 采样，现场推杆）**

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 速度环输出 `sOut` | ±20000 每 20 ms 翻转（饱和） | 最大 **865**（满量程 4%），平稳 |
| 实际转速 `spd` | ±500°/s 乱跳（max 3072） | 平滑跟随，max **102°/s** |
| 角度 | 抽搐/几乎不动 | 平滑扫过（262°→241°，≈50°/s） |

**现场手感（用户实测反馈）**：**"跟手、平稳，不抖了"** ✓

**遗留小项（可选优化）**：摩擦前馈是"方向性常值"，所以小指令时实际转速会略快于指令
（实测 指令 −10.3°/s 时实际 −18°/s；指令 −27.5°/s 时实际 −54°/s）。若希望低速更线性，可把前馈改为
"按指令比例 + 上限"（如 `ff = clamp(0.35×ref, ±GIMBAL_YAW_FRICTION_FF)`）并保留一个最小死区补偿值。

**固件**：`GIMBAL_BOARD` FLASH 117336 B，MD5 `53FE974923F60D1BB30685B2E942023A`（已烧录 + 回读 PASS）。

> **操作/回退请见《云台底盘操作与回退手册_2026-10-15.md》**（驾驶与示教操作步骤、参数速查、各条回退宏、
> 排查决策树与已知硬件坑）。

### 9.23 小陀螺"推前进却画圈"的根因：大yaw 失去了**世界系基准**（2026-10-15 深夜，已修 + 已烧录）

**现象（用户现场）**：右开关[上]进小陀螺，右摇杆前推 → 车**不直行，而是画圈**。

**根因链（4 步，全部有代码位置）**

| # | 环节 | 位置 |
| --- | --- | --- |
| 1 | 摇杆给的是"**云台系**"速度指令，底盘侧用 `offset_angle` 把它旋到**车体系**再用 | `chassis.c:1016-1027` |
| 2 | `offset_angle` = **大yaw 电机相对底盘的编码器角**（云台板算好，随 `0x312` 下发） | `robot_cmd.c:174-211`（取值 `:179`）、`gimbal.c:288` |
| 3 | 大yaw 现在是**速度环**，摇杆回中时参考值 = 0 ⇒ 大yaw 只保证"**相对底盘不转**" | `gimbal.c:266-267` |
| 4 | 小陀螺 = 底盘绕自身转（`wz=25`，`chassis.c:988`）⇒ 大yaw **被底盘带着一起转** ⇒ 电机相对角恒定 ⇒ `offset_angle` **冻结** | — |

于是底盘收到的是**永远钉在车体系里**的恒定速度指令 —— "车体系内恒定速度 + 车体自转" 在数学上就是一个
**圆周（半径 = v/ω）**，所以现象必然是"画圈"而不是"不动"。

**一句话**：`GIMBAL_GYRO_MODE` 的原设计含义是"大yaw 用 IMU **绝对指向**"（`robot_def.h:181-182`），
小陀螺/跟随都靠它当**世界系基准**；为压住抖动改成"相对底盘锁零"的速度环后，基准丢了。
**跟随模式看不出来**（它只需要相对角：`NO_FOLLOW` 直接强制 `offset=0`，`FOLLOW` 用 PID 把 offset 拉到 0），
**只有小陀螺必然暴露**。

**修复**：新增 `GIMBAL_YAW_IMU_HOLD`（只影响云台板）——在速度环**外面**加一层"IMU 世界角保持"：
摇杆在推时保持环让位并把目标刷新为当前指向（**手感与原来完全一致**），摇杆回中/小陀螺时用
`+Kp·wrap(target − BigYaw_Feed)` 补出保持速率 ⇒ 大yaw 钉在世界系 ⇒ `offset_angle` 随底盘自转连续变化
⇒ 底盘按**大yaw 朝向**直行（左摇杆还能改朝向），并顺带获得"松杆钉住角度"。

**符号（+1）怎么定死的——不用新做实验，直接从既有日志里量出来**：`yawwatch2.log` 的 t=15.2~17.0
（当时底盘静止在 `NO_FOLLOW`，排除底盘自转干扰），同一时段三路信号同向上升：

| 采样 t(s) | 电机 `spd`(°/s) | 电机**自身单圈角**(°) | IMU `YawTotal`(°) |
| --- | --- | --- | --- |
| 15.2 | +36.0 | 327.39 | −6.21 |
| 15.4 | +42.0 | 338.24 | +4.26 |
| 15.7 | +48.0 | 350.81 | +16.35 |
| 15.9 | +60.0 | 5.71 | +32.00 |
| 16.4 | +54.0 | 35.02 | +81.80 |

速率也吻合（电机 ≈ +50°/s vs IMU ≈ +52…+100°/s）⇒ **速度环正速率 ⇒ `BigYaw_Feed` 增大**
⇒ 保持环必须写成 `+Kp·(target − fb)`（反之就是正反馈跑飞）。
（`yawwatch1.log` t=17.7~17.9 的负速率段：`spd=−77/−192`、`YawTotal 304→224` 反向下降，同样成立。）

**参数与限幅**：`GIMBAL_YAW_HOLD_KP = 8.0`（量纲 1/s）——底盘自旋 ω 时稳态会有一个 **ω/Kp 的固定偏差**
（ω=150°/s ⇒ 约 19°），嫌"瞄的方向偏"就加大 Kp 或加外环积分，出现嗡嗡抖就减小；
保持环单独限幅 `GIMBAL_YAW_HOLD_LIMIT = 150°/s`，合并后仍受 `GIMBAL_YAW_SPEED_LIMIT = 200°/s` 兜底。

**固件**：`GIMBAL_BOARD` FLASH **117624 B**，MD5 `02C899CE2FBB96ACC457AF10AE3329C1`
（已烧录 + 全片回读 **PASS，0 mismatch**）。底盘板**未改动**（仍是 `77065A1E…`）。

> 解析符号（`jlink_tool.py:907-926`），换板型后符号会静默错配。本次烧录后自行确认了目标板身份：

**遗留/待现场确认**

   若要"指哪走哪"，再补一项"底盘自转速率前馈"（测量式：`d(BigYaw)/dt − speed_aps`，符号已确定）。
2. **小陀螺分支的平移系数是 `5.0`**，另两档是 `25.0`（`robot_cmd.c:291-292`）⇒ 即使直行了，前进速度只有
   其它档的 1/5，待确认是否故意（疑似调试残留）。
3. 启用保持后**松杆会钉住世界朝向**（原设计行为）：人为拨动云台会感到回弹，属预期。

### 9.24 IMU 不可用时的兜底：小陀螺开环前馈（常数**在线自学**，2026-10-16）

**起因（用户提问）**："可不可以不用 IMU 标定，只用大yaw 电机来，或者其他方法？"

**先给原理结论（这条堵死了"只用大yaw电机"）**：大yaw 电机的编码器测的是**"云台相对底盘"**的转角；
底盘自转时只要云台还跟着底盘（相对角不变），该编码器读数**恒定** —— **底盘自转对这个传感器不可观测**。
想让它当世界基准，前提是大yaw 相对**世界**不动，而"相对世界不动"只能由惯性/外部测量给出。
"让大yaw 空着靠惯性当基准"同样不成立：本轴静摩擦很大（前馈需 12.5% 占空比 ≈0.15 N·m），
自由云台被底盘拖同步的特征时间只有**几十毫秒**。

**标定到底值不值（实测，本次上电正是"标定失败 + 离线常数"启动）**：

| 量 | 实测 |
| --- | --- |
| `BigYaw_Feed` 漂移（24 s） | **−0.43 °/s**（残余零偏 gx/gy/gz = +0.47 / −0.82 / −0.019 °/s） |
| 小陀螺推杆 3 s 的航向误差 | ≈ **1.3°**（可忽略） |
| 标定成功的成本 | **3 s**（`CaliTimes=6000 × 0.5 ms`），条件是这 3 秒**别碰车**；被晃动时一轮轮重试、最长 12 s 上限后放弃 |

⇒ 结论：**标定失败不影响小陀螺使用**；反过来**跳过标定只会让漂移更大**（gx/gy 的 0.47 / −0.82 °/s 会漏到航向），
所以"不想依赖标定"的正确做法不是关掉它，而是**减少对绝对角的依赖** —— 即下面这条兜底。

**兜底设计（不需要任何传感器、不需要人工标定）**

| 环节 | 做法 |
| --- | --- |
| 让云台知道"在不在小陀螺" | `robot_cmd` 在 `CHASSIS_ROTATE` 档把 `Gimbal_Ctrl_Cmd_s.chassis_rotate_wz`（该字段原先只声明未使用、且**不过CAN**）填成 `GIMBAL_YAW_SPIN_FF_RATE`；其它档在 `RobotCMDTask` 里每拍清零 |
| 兜底常数的**在线自学** | 保持环在"小陀螺 + 松杆 + 未饱和"且已稳定 1 s 后，把稳态输出低通学进 `yaw_ff_learned`（α=0.002@1kHz ⇒ τ≈0.5 s，越界±300°/s 即丢弃）。**保持环稳态输出恒等于"抵消底盘自转所需的反向速率"**，所以这个值自带正确符号，无需人工标定 |
| IMU 失效时切换 | `!isfinite(BigYaw_Feed) \|\| !INS_IMUIsAvailable()` ⇒ 保持环失效，改叠加 `yaw_ff_learned`；没学到过才退回 `robot_def.h` 初值 `58.0°/s`（几何估算） |
| 强制验证 | `GIMBAL_YAW_FF_FORCE` 宏可关掉保持环、只走兜底 —— 用于现场确认兜底方向（方向反了的表现是**"画得更紧"而不是跑飞**，安全） |
| 新增接口 | `INS_IMUIsAvailable()`（`ins_task.c` 的 `IMU_Available` 是 `static`，外部取不到；gimbal.c 需要它判断姿态是否可信） |

**现场怎么确认学到了**（两条路，任选）：

```powershell
# ① 看日志(最省事): 小陀螺里稳定 1s 后, 云台板 RTT 每秒打一行
#    I:[gimbal] spin FF learned = -58200 mdeg/s      (= -58.2°/s, 就是需要补偿的自转速率)
python jlink_tool.py status gimbal
# ② 直接读内存(符号地址随固件变化, 先用 nm 查)
arm-none-eabi-nm cmake-build-verify\gimbal_fixed.elf | findstr yaw_ff_learned
python jlink_tool.py peek 200082BC 8 gimbal
```

**固件**：`GIMBAL_BOARD` FLASH **117984 B**，MD5 `2D65B79F953973FF9E47130CFBFE0CC9`（烧录 + 回读 PASS）。底盘板未改动。

**已知不足（下次可加固）**：`INS_IMUIsAvailable()` 只覆盖"初始化失败"；若是**运行中 SPI 失效**（BMI088 通信断但值冻结），
姿态既不是 NaN 也不是 0，保持环会拿着冻结值闭环（误差被"推杆重刷目标"限制在小角度 ⇒ 最坏是几十 °/s 缓慢自转）。
可加"电机在转但 `BigYaw` 连续 200 ms 不动 ⇒ 判姿态冻结、关保持环切兜底"。

## 附录 A：双板转发路线的遗留缺陷（启用 `RC_RECEIVER_ON_CHASSIS` 前**必修**）

> **状态（2026-10-15）：已修复并实测定位确认。** 现场把配置切回双板（`CHASSIS_BOARD`，`CHASSIS_RC_DIRECT` 关闭）后，
> 云台板在线持续发 `0x312`，底盘板实测 `recv_data_len=21 / recv_buf_len=25`、接收状态**恒定停在 24/25 字节**、
> `crc_err=0 / tail_err=0`、`resync=9287`（修复了接收端重同步后才可见），daemon 恒离线 ——
> **与本节预测的"前 3 帧占满 3 个邮箱、第 4 帧被丢弃"完全一致**（差 1 字节无法收尾）。
> 修复内容见下方"修复实施"段。

本节不是本次故障的原因（本次已改用单板直控），但 §1–§8 的转发路线在修复前**100% 不通**，
故登记在此，避免日后直接启用。

**现象预测**：底盘板 RTT 中 `[bsp_can] CAN mailbox full! failed to add msg` 每秒数百条；
云台板每秒一条 `[can_comm] can comm rx[311] lost, reset rx state.`；
两侧 `CANCommIsOnline()` 恒 0，遥控器数据永远送不到 `robot_cmd`。

**机理（实测结构体大小 + 源码）**：

| 项 | 值 / 位置 |
| --- | --- |
| 工程使用短枚举 | `sizeof(Bullet_Speed_e) = sizeof(Enemy_Color_e) = 1`（gdb 读 `.elf`） |
| `Chassis_Upload_Data_s` | **38 B**（改造前为 3 B，`git show HEAD:application/robot_def.h`） |
| `Chassis_Ctrl_Cmd_s` | **21 B** |
| `0x311` 上行包 | 38 + 4（`CAN_COMM_OFFSET_BYTES`）= 42 B → **连发 6 帧** |
| `0x312` 下行包 | 21 + 4 = 25 B → **连发 4 帧** |
| bxCAN 发送邮箱数 | **3** |
| 发送路径 | `can_comm.c:123-129` 一次性连发；`bsp_can.c:140-147`（`CAN_TX_NONBLOCKING=1`）邮箱满即 `return 0`，**无重试、无队列** |
| 接收路径 | `can_comm.c:55` 要求收满 `recv_buf_len` 才校验帧尾/CRC8 → 缺帧即永远判离线 |
| 误判来源 | 《底盘板缺陷修复清单与编码规则》§A.3（`:82`）以「所有调用点都忽略返回值」为据认定丢帧安全 —— 该前提对**多帧协议 `CANComm` 不成立** |

即：第 4 帧起必被丢弃，接收端永远凑不齐一包；改造前 `0x311` 只有 7 B（1 帧）能通，
本次改造把它推到 6 帧后彻底不可用。`0x312`（4 帧）自 `4bac4df`（S3 非阻塞重写）起即已受损。

**修复要点（建议顺序）**：

1. `bsp_can` 新增"带 µs 级截止时间的等邮箱"接口（`HAL_CAN_GetTxMailboxesFreeLevel` + `DWT_GetTimeline_us()`），
   **只**供多帧协议使用；不改 `CANTransmit()` 语义、不动 9 处电机调用点（避免把阻塞引回 1 kHz MotorTask）。
2. `CANCommSend()` 逐帧确认：等不到空闲邮箱或 `CANTransmit` 失败 → **作废整包**、计数（如 `tx_fail_count`）并限频告警，
   下一周期从帧头重发；调用点（`chassis.c` / `robot_cmd.c`）不再一律忽略返回值。
3. 接收端 `CANCommRxCallback()` 在 `recv_state==1` 中途允许"新帧头"重同步（修 `S1/C3`），
   并给 **datalen 不匹配**加日志/计数（这是"两板固件不同源"的唯一可观测点——旧云台固件 `recv_data_len=3`，
   新底盘板发 38，会被静默拒收）。
4. `CANCommInit()` 前置校验 `data_len + CAN_COMM_OFFSET_BYTES <= CAN_COMM_MAX_BUFFSIZE`。
5. **两板必须同源编译烧录**（云台侧改动需先合入实际使用的 `gimbal_IMU` 分支），记录两枚 `.bin` 的 md5。
6. 可选降载：若实测 CAN1 负载偏高，裁剪 `RC_Data_s`（如 `key_count[16]`）或把 `0x311` 上传降到 100 Hz；
   注意 3 帧恰为邮箱数上限，单纯缩包不能替代第 1、2 项。

### B.2 已核实为安全的项（免复查）

- 附录 A 机理独立复验：`bsp_can.c:135` `CAN_TX_NONBLOCKING=1` 使 `CANTransmit` **忽略 timeout 参数**、邮箱满立即 `return 0`；bxCAN 仅 3 个发送邮箱；`can_comm.c:123-129` 微秒级连发 vs 1 Mbps 单帧约 110–130 µs → 第 4 帧起必丢；`Src/can.c:50/82` `AutoRetransmission=ENABLE` 使无对端 ACK 时邮箱长期占满 —— 全部成立。
- 尺寸实测（静态断言 + 实际工具链 arm-none-eabi-gcc 14.3.1）：短枚举 1 B、`RC_Data_s` 35 B、`Chassis_Upload_Data_s` 38 B（改造前 3 B）→ 6 帧/4 帧结论成立。
- 直控断连保护链：RC daemon `reload=10`@100 Hz = 100 ms；上电 1 s 宽限期内 `rc_ctrl` 全 0 → `switch_right=0` 落 `default` → 零力，不会误动。
- `EmergencyHandler`（robot_cmd.c:594）在遥控镜像刷新（:575）**之后**调用，取值为本拍数据。
- `robot_cmd.c` 全量 grep 核对：实际只消费 `RC_Data_s` 已覆盖字段（摇杆/开关/拨轮/`mouse.x/y`/`key[KEY_PRESS]`/`key_count[KEY_PRESS]`）；`mouse.press_l/r`、`KEY_PRESS_WITH_CTRL/SHIFT` 当前无消费 → §7.2 字段缺口**现状下不构成功能问题**（仅未来扩展需同步）。
- `DaemonTask` 在底盘板无条件创建（robot_task.h:49）→ `RemoteControlIsOnline()` 底盘板可用。
- USART3 在底盘板构建中唯一占用（HC05/舵机电调/裁判系统/视觉的 Init 均未在底盘板调用）。
- CAN ID 无冲突：`0x311/0x312/0x313` 与电机 `0x200/0x1FF/0x2FF` 系不重叠。
- 当前树（`CHASSIS_BOARD` + `CHASSIS_RC_DIRECT`）重编 0 error / 0 warning，RAM 76928 B / FLASH 103300 B，与 §9.4 一致。
- `INS_Init()` 幂等（ins_task.c:90-93），三处调用无副作用（见 B-7 撤销说明）。
