## 1 使用说明

### 1.1 本文解决的问题

把 660 余页的规则文档与 85 页的通信协议压缩成“可逐条勾选”的核对单元：每一条协议条目都并列给出**报文格式**、**字段与取值**、**代码位置**、**使用场景**与**判定结论**，使协议实现是否正确不再依赖通读代码，而是按表核对。

## 2 协议总体框架

### 2.1 串口物理参数与波特率

串口部分固定为：**8 位数据位、1 位停止位、无校验位、无硬件流控**。三条链路的波特率不同，接错串口或配错波特率表现为“帧头永远等不到 0xA5”。

| 物理接口 | 波特率 | 本仓库对应 | 说明 |
| --- | --- | --- | --- |
| 电源管理模块 ←→ 机器人 | 115200 | `huart6 / USART6` | 常规链路，裁判系统主数据通道（本文主体） |
| 自定义控制器 ←→ 选手端 | 115200 | 未使用 | 非链路数据 0x0306 |
| 图传发送端 ←→ 机器人 | 921600 | 未使用 | 图传链路 0x0302 / 0x0309 / 0x0310 / 0x0311 |

代码侧配置见 `Src/usart.c:106-113`：`BaudRate=115200`、`WORDLENGTH_8B`、`STOPBITS_1`、`PARITY_NONE`、`HWFLOWCTL_NONE`，与表 1-1 一致。**【一致】**

### 2.2 三条数据链路

| 链路 | 路径 | 本仓库状态 | 后果 |
| --- | --- | --- | --- |
| 常规链路 | 裁判系统服务器 → 主控模块 → 电源管理模块 User 串口 → 机器人 | 已接（USART6） | 0x0001~0x0308 全部走这条 |
| 图传链路 | 裁判系统选手端 ↔ 图传模块（发送端）↔ 机器人 | 未接 | 自定义控制器/客户端相关命令码全部不可用 |
| 雷达无线链路 | 信号发射源 → 雷达（电磁波，非串口） | 不适用（步兵无雷达） | 0x0A01~0x0A06 与本车无关 |

### 2.3 帧格式

一帧 = **5 字节帧头 + 2 字节命令码 + n 字节数据 + 2 字节 CRC16**，最小 9 字节。所有多字节字段（`data_length`、`cmd_id`、结构体内 `uint16/uint32/float`）均为**小端**。

| 段 | 长度 | 内容 | 代码 |
| --- | --- | --- | --- |
| frame_header | 5 B | SOF(0xA5) + data_length(2B) + seq(1B) + CRC8(1B) | `xFrameHeader` |
| cmd_id | 2 B | 命令码，小端 | `CmdID` |
| data | n B | 命令码对应的数据段，n 由各命令码固定规定 | 各 `ext_*_t` 结构体 |
| frame_tail | 2 B | CRC16，整包校验（含帧头与命令码） | `frametail` |

| 域 | 偏移 | 大小 | 说明 |
| --- | --- | --- | --- |
| SOF | 0 | 1 | 固定 0xA5 |
| data_length | 1 | 2 | **只统计 data 长度**，不含帧头/命令码/CRC16。（易错点：不少实现误加 9） |
| seq | 3 | 1 | 包序号，发送方自增 |
| CRC8 | 4 | 1 | 对前 4 字节做 CRC8 |

代码中的偏移与长度宏（`referee_protocol.h:28-43`）：`FRAME_HEADER_Offset=0 / CMD_ID_Offset=5 / DATA_Offset=7`，`LEN_HEADER=5 / LEN_CMDID=2 / LEN_TAIL=2 / LEN_CRC8=4`，与协议完全对应。**【一致】**

### 2.4 CRC 校验

| 项 | CRC8（帧头） | CRC16（整包） |
| --- | --- | --- |
| 多项式 | G(x)=x⁸+x⁵+x⁴+1 | G(x)=x¹⁶+x¹²+x⁵+1（查表 0x8408 反射式） |
| 初值 | 0xFF | 0xFFFF |
| 覆盖范围 | SOF + data_length + seq，共 **4 字节** | frame_header + cmd_id + data，共 **7+n 字节** |
| 结果位置 | 帧头第 5 字节（偏移 4） | 帧尾 2 字节，**低字节在前** |
| 代码 | `modules/referee/crc_ref.c`：CRC8 表 `:6-24`、CRC16 表 `:28-62`、函数 `:79-`；表内容与协议附录一逐字节一致 |  |

调用方式：`Verify_CRC8_Check_Sum(buff, LEN_HEADER)` 传“含校验字节”的长度 5，函数内部按 `dwLength-1` 计算再比对末字节，语义正确；`Verify_CRC16_Check_Sum(buff, judge_length)` 同理。**【一致】**

### 2.5 链路质量对控制的影响

| 工况 | 延迟 | 丢包率 | 实现约束 |
| --- | --- | --- | --- |
| 正常工作 | 约 130 ms | < 1% | 数据只能用于“慢环”：功率上限、热量上限、状态机、UI 显示；**禁止进入 1 kHz 姿态环或 200 Hz 速度环**（130 ms 延迟在闭环里等于相位滞后 47°@1 Hz） |
| 赛场网络较差 | 约 200 ms | 约 3% |  |

本仓库的现状是“裁判系统数据只用于 UI、未进入控制环”，这一点是安全的；但第 9 章 P0-1 指出该通道当前连初始化都没做，需先修复再谈使用。

### 3.4 步兵最小可用实现顺序

按“先让链路可信、再让数据可用、最后补策略数据”的顺序推进，每一步都有可验证的判据，避免一次性改太多无法定位问题。

| 步 | 做什么 | 对应条目 | 验证判据 |
| --- | --- | --- | --- |
| 1 | 恢复裁判系统初始化、消除空指针 | P0-1（第 9.1 节） | 上电不 HardFault；不再向串口发垃圾帧 |
| 2 | 按 2026 版重写 5 个结构体与长度宏 | 0x0003 / 0x0201 / 0x0202 / 0x0203 / 0x0204 | `_Static_assert` 全部通过 |
| 3 | 打通 0x0301，先把 UI 画出来 | 0x0301 + 0x0100 / 0x0101 | 选手端能看到自绘图形与字符 |
| 4 | 接入热量与功率上限 | 0x0201 + 0x0202 | UI 显示的热量/上限与选手端一致 |
| 5 | 接入余弹，做停射保护 | 0x0208 | 余弹归零时拨弹停转 |
| 6 | 接入血量与场地事件 | 0x0003 + 0x0101 | 血量数值与选手端逐点核对一致 |
| 7 | 接入比赛阶段，驱动状态机 | 0x0001 | 准备/比赛中/结算三态切换正确 |
| 8 | 补判罚提示与增益显示 | 0x0104 + 0x0204 | 被黄牌时 UI/蜂鸣器有响应 |

> **注意**　**顺序不可颠倒的原因：**第 1、2 步是“数据可信”的前提，跳过它们直接做第 4 步，会把“字段错位导致的假数据”当成“控制参数没调好”，白花大量现场时间。第 3 步放在前面则是因为 UI 是唯一能“用眼睛直接验证整条链路”的手段——图形画得出来，说明帧头、CRC、组包、ID 全对。

## 4 上行数据逐条核对（0x0001 ~ 0x020E）

### 4.6 0x0201 机器人性能体系（17 B，10 Hz，主控→本机）

这是步兵最核心的一帧：热量上限、冷却、底盘功率上限、弹速上限全在这里。2026 版新增 **float bullet_speed_limit**（4 B），导致电源输出字节从偏移 12 后移到 **16**。

| 偏移/大小 | 协议字段 | 类型与取值 | 代码字段（现状） |
| --- | --- | --- | --- |
| 0 / 1 B | robot_id | 1-11 红 / 101-111 蓝（见附录 B） | robot_id ✔ |
| 1 / 1 B | robot_level | uint8 等级 | robot_level ✔ |
| 2-3 / 2 B | current_HP | uint16 当前血量 | current_HP ✔ |
| 4-5 / 2 B | maximum_HP | uint16 血量上限 | maximum_HP ✔ |
| 6-7 / 2 B | shooter_barrel_cooling_value | uint16，热量/秒冷却值 | shooter_barrel_cooling_value ✔ |
| 8-9 / 2 B | shooter_barrel_heat_limit | uint16，热量上限 | shooter_barrel_heat_limit ✔ |
| 10-11 / 2 B | chassis_power_limit | uint16，底盘功率上限（W） | chassis_power_limit ✔ |
| 12-15 / 4 B | **bullet_speed_limit** | **float，射击初速度上限（m/s）** | **缺失**（未定义该字段） |

```text
typedef struct {              // 现状（13 B，缺 bullet_speed_limit）
  uint8_t robot_id; uint8_t robot_level;
  uint16_t current_HP, maximum_HP;
  uint16_t shooter_barrel_cooling_value, shooter_barrel_heat_limit;
  uint16_t chassis_power_limit;
```

> **风险**　**判定：【需修正 · P0】**长度 13 ≠ 17。偏移 0~11 的 7 个字段侥幸对齐，从第 12 字节开始全错：`power_management_*` 读到的是 `bullet_speed_limit` 这个 float 的**最低字节**（例如 30.0f = `0x41F00000`，最低字节为 `0x00`，于是三个口全被判为“无输出”）；`bullet_speed_limit` 则完全收不到。而弹速上限是弹道解算与摩擦轮转速设定的直接输入，缺它会导致“限速 15 m/s 时按 30 m/s 解算”的系统性偏差。

**使用场景：**① 热量闭环（`shooter_barrel_heat_limit` 与 0x0202 的实时热量配对，决定能否连发）；② 功率控制（`chassis_power_limit` 是底盘功率 PID 的限幅值）；③ 摩擦轮目标转速（由 `bullet_speed_limit` 反查）。目前 ①② 已有数据可用，③ 因字段缺失无法实现。

## 5 机器人交互数据 0x0301 与 UI 子协议

0x0301 是唯一一条“机器人自己组包发送”的命令码：既承载选手端 UI 绘制，也承载机器人之间的自定义通信。它的结构与固定命令码不同——**数据段内部还有一层 6 字节头**，用“子内容 ID”区分不同用途。

### 5.1 数据段结构与带宽预算

| 偏移/大小 | 字段 | 取值约束 | 代码字段 |
| --- | --- | --- | --- |
| 0-1 / 2 B | data_cmd_id 子内容 ID | 必须是协议开放的子内容 ID | datahead.data_cmd_id |
| 2-3 / 2 B | sender_id 发送者 ID | 必须等于自身机器人 ID（附录 B） | datahead.sender_ID |
| 4-5 / 2 B | receiver_id 接收者 ID | UI：己方选手端 ID（0x0100 + 机器人 ID）；<br>机间通信：己方机器人 ID | datahead.receiver_ID |
| 6… / x B | 内容数据段 | **x ≤ 112** | Graph_Data_t / String_Data_t 等 |

| 约束 | 数值 | 含义 |
| --- | --- | --- |
| 单包总长 | ≤ 127 B | 127 − 9（帧头+命令码+帧尾）− 6（数据段头）= 112 B 内容上限 |
| 上行频率 | ≤ 30 Hz | 2026 版由旧版 10 Hz 提高到 30 Hz；代码注释仍写 10 Hz（见 9.3） |
| 接收带宽 | 3720 B / 1000 ms（步兵） | 雷达与哨兵为 5120 B/1000 ms |

**带宽换算（步兵）：**3720 B/s ÷ 118 B ≈ **31 帧/秒**，即“打满 30 Hz 就没有余量给机间通信”。若同时要发 UI 与自定义数据，需自行分配配额（例如 UI 20 Hz + 自定义 10 Hz）。

### 5.7 0x0200 ~ 0x02FF 机器人间自定义通信

协议只规定“子内容 ID 落在 0x0200~0x02FF、内容 ≤112 B、30 Hz 上限”，具体字段由队伍自定。本仓库 `referee_protocol.h:275（Communicate_Data_ID=0x0200）`、`:298-317` 定义了 5 字节数据体与收发结构体，`referee.md:170-195` 给出了示例实现 `CommBetweenRobotSend`，但**仓库里并不存在该函数的实现**（`.c` 文件中无此符号）。

**判定：【仅定义】**。接收侧见 9.2 的 P1-4：`LEN_receive_data` 被写死为 `6 + Communicate_Data_LEN`，意味着只接收 5 字节自定义数据，且不校验子内容 ID——任何 0x0301 帧（包括 UI 回包）都会被塞进同一个缓冲区。

### 6.4 雷达无线链路（0x0A01 ~ 0x0A06）

这 6 条由信号发射源直接发给雷达（电磁波链路，非串口），本车无雷达，**全部不适用**。仅在需要向雷达组提供数据格式参考时查阅：0x0A01 位置（12×2 B）、0x0A02 血量（12 B，含 1 个保留位）、0x0A03 发弹量（10 B）、0x0A04 宏观状态（8 B）、0x0A05 增益与姿态（41 B）、0x0A06 干扰波密钥（6 B ASCII）。

### 6.5 自定义客户端协议（第 2 章，MQTT + Protobuf）

| 项 | 内容 |
| --- | --- |
| 传输 | MQTT（topic = 指令名），载荷为 Protobuf v3 序列化二进制；服务器固定 IP `192.168.12.1:3333`，客户端 `192.168.12.2` |
| 图传码流 | UDP 监听 3334；每包前 8 B 为「帧号(2) + 分片序号(2) + 帧总字节(4)」，**大端**；单包 ≤1400 B，HEVC/H.265，60 fps，无重传 |
| 指令规模 | 36 条（KeyboardMouseControl、CustomControl、GameStatus、GlobalUnitStatus…、CommonCommand 等），QoS 最高 1，频率 1~75 Hz |

**判定：【未实现，且与本车 MCU 无关】**。这部分跑在“自定义客户端”（PC/平板）上，通过网口与赛事引擎通信；车端只通过 0x0310/0x0311 与它交换 300/30 字节，而这两条图传链路命令码尚未实现。若要做视觉/自瞄上位机，走的其实是 0x0310/0x0311，而不是本章的 MQTT。

## 7 收发流程与交互顺序

### 7.1 接收链路：从字节到结构体

| 步 | 动作 | 代码位置 | 说明 |
| --- | --- | --- | --- |
| 1 | 串口空闲中断/DMA 完成 | `bsp_usart.c:103` | 关半传输中断，只在 IDLE 或全满时进回调 |
| 2 | 按句柄找到实例并调用模块回调 | `bsp_usart.c:108-110` | 裁判系统注册的回调是 `RefereeRxCallback` |
| 3 | 喂狗 + 解析 | `rm_referee.c:110-114` | `DaemonReload` 重置 30 拍（0.3 s）超时 |
| 4 | 帧头/CRC8/长度/CRC16/命令码分发 | `rm_referee.c:33-107` | 成功则 memcpy 到对应成员 |
| 5 | 清空缓冲并重启 DMA 接收 | `bsp_usart.c:111-115` | 按 `Size` 清零 |

### 7.2 单帧解析的判定顺序（严格按此顺序，错一步就会误判）

```text
1. memcpy 帧头 5 B → 2. buff[0] == 0xA5 ?
3. Verify_CRC8(buff, 5) 通过 ?
4. judge_length = buff[1] + 5 + 2 + 2        // data_length 取低字节
5. Verify_CRC16(buff, judge_length) 通过 ?
6. CmdID = buff[5] | (buff[6] << 8)          // 小端
7. switch(CmdID) → memcpy(buff + 7, 长度宏)
8. 若 buff[judge_length] == 0xA5 → 递归解析下一帧
```

这 8 步中，**第 4 步与第 8 步**是本仓库的两个薄弱环节：`data_length` 是 2 字节而代码只取低字节（>255 时溢出）；第 8 步的递归没有“剩余长度是否足够”的检查，且没有深度上限。详见 9.2 P1-2/P1-3。

### 7.3 发送组包顺序（以 UI 为例）

| 步 | 动作 | 代码位置 / 说明 |
| --- | --- | --- |
| 1 | 填帧头：SOF=0xA5，DataLength，Seq | DataLength 只算 data 段（6 + 15×cnt 或 6+2 / 6+45） |
| 2 | 算 CRC8 填入第 5 字节 | `Get_CRC8_Check_Sum(&buf, 4, 0xFF)` |
| 3 | 填 CmdID=0x0301、子内容 ID、sender/receiver | sender=自身机器人 ID，receiver=0x0100+自身 ID |
| 4 | 填内容（图形数组或字符） | 图形按 15 B 紧密排列 |
| 5 | 算 CRC16 填入帧尾 2 字节（低字节在前） | `Append_CRC16_Check_Sum(buf, 总长)`，内部按 总长-2 计算 |
| 6 | DMA 发送 + **osDelay(115)** | `rm_referee.c:145-149`：每包强制等 115 ms |

> **风险**　**频率后果：**115 ms/包 ⇒ 理论最高 **8.7 包/秒**。协议给 0x0301 的上限是 30 Hz，UI 初始化时 `MyUIInit` 连发 12 包，光初始化就要 **约 1.4 s**；若将来把多机通信也走 `RefereeSend`，等于把 30 Hz 的配额压到 8.7 Hz。这个延时是“防裁判系统缓冲溢出”的保守做法，但应与协议上限对齐（建议改 33 ms，或做成“最小间隔 + 非阻塞时间戳”）。

### 7.5 请求 / 响应配对关系

裁判系统大部分是“服务器单向推送”，真正具备“请求→反馈”语义的只有少数几条。做状态机时按此表配对，才不会出现“发了指令不知道成功没有”。

| 机器人 → 服务器（请求） | 服务器 → 机器人（反馈） | 配对关系与注意事项 |
| --- | --- | --- |
| 0x0120 哨兵自主决策 | 0x020D 哨兵状态 / 0x0208 金币 / 0x0003 血量 | 累计计数器语义；服务器按“低位→高位”顺序处理，任一步失败则忽略后续 |
| 0x0121 雷达自主决策 | 0x020E 雷达状态 / 0x020C 标记进度 | 双倍易伤有次数上限；密钥验证 10 s 内重复无效 |
| 0x0301 UI 绘制 | 无应答 | 纯单向；可靠性靠 `seq` 与重复发送，不靠 ACK |
| 0x0303 地图点击（服务器→车） | 无 | 服务器自动补发 4 次 + 1 Hz 定频，车端必须幂等 |
| 0x0308 自定义消息 | 无（选手端显示） | UTF-16，注意大小端 |
| 0x0310 / 0x0311 自定义客户端 | 双向，互不确认 | 协议明确“数据量大，无重传机制”，需自行加序号/校验 |
| —（被动） | 0x0206 伤害 / 0x0207 射击 | 事件型推送，只在发生时发一次，不可轮询 |

### 7.6 频率预算（步兵视角）

| 方向 | 带宽/频率 | 备注 |
| --- | --- | --- |

## 9 一致性问题与风险清单

按“会不会导致功能错误/能否静默出错”分级：**P0** 必错或必崩；**P1** 功能受限或存在健壮性隐患；**P2** 规范与可维护性问题。每条都给出证据行号，可逐条复核。

### 9.1 P0：数据必然错误或系统不稳定

| 编号 | 问题 | 证据 | 影响 |
| --- | --- | --- | --- |
| P0-1 | 裁判系统从未初始化，UI 任务却被创建 | `chassis.c:475` 注释掉 `UITaskInit`；`robot_task.h:55-58` 仍创建任务；`referee_task.c:19/64` 用空指针 | 见下文详述 |
| P0-2 | 0x0003 按 32 B 解析，协议 20 B | `referee_protocol.h:126-144`、`:93` | 己方 5~8 字段与对方全部字段错位，多读 12 B 越界 |
| P0-3 | 0x0201 按 13 B 解析，协议 17 B | `:162-174`、`:96` | 弹速上限丢失；电源输出位错读成 float 最低字节 |
| P0-4 | 0x0202 按 16 B 解析，协议 14 B 且前 8 B 已废弃 | `:177-186`、`:97` | 功率恒为 0；42mm 热量读到 CRC16 帧尾（假数据） |
| P0-5 | 0x0203 按 16 B 解析，协议 12 B | `:189-195`、`:98` | z 被赋成角度（量纲错）、yaw 越界；导航类功能不可用 |
| P0-6 | 0x0204 协议 8 B / 结构体 7 B / 长度宏 6 B 三者不一致 | `:198-205`、`:99` | attack_buff 只拷低字节；remaining_energy 缺失 |

> **风险**　**P0-1 展开（最需要先处理的一条）：**当前构建 `GIMBAL_BOARD` 下，`OSTaskInit` 会创建 UI 任务（因为只排除了 `CHASSIS_BOARD`），而 `referee_recv_info` 这个文件级静态指针**永远是 NULL**——全仓库没有第二处调用 `UITaskInit`。`MyUIInit` 第一句就解引用它读 `init_flag`。<br><br>更隐蔽的是：在 STM32F4 上，低地址 `0x0000_0000` 段是**启动存储器别名区**（从 Flash 启动时映射到 Flash 起始），所以 `NULL->init_flag`（偏移约 0x8A）很可能**读到中断向量表里的字节而不触发 HardFault**——值非 0 就“侥幸通过”判断，接着 `while (robot_id == 0)` 也会读到非 0 值而立即退出，然后进入 `UIDelete → RefereeSend → USARTSend(NULL,...)`，在 `bsp_usart.c:72` 取 `_instance->usart_handle` 时再次读低地址，把垃圾当 `UART_HandleTypeDef*` 传给 `HAL_UART_Transmit_DMA`。<br><br>结果是三种之一：**HardFault 复位循环**、**HAL 内部指针野跑**、或**不崩但持续向 USART6 发 sender_id/receiver_id 全是垃圾的 0x0301 帧**（污染裁判系统链路）。三种都属于“上电即不可用”，而且第二种最难定位。<br><br>**修法（二选一）：**① 恢复 `chassis.c:475` 的 `referee_data = UITaskInit(&huart6, &ui_data);` 并补回 `static Referee_Interactive_info_t ui_data;` 与 `static referee_info_t *referee_data;`（`chassis.c:98` 的声明也被注释了）；② 若暂时不用 UI，则把 `robot_task.h:56-57` 的任务创建一并注释，并在 `MyUIInit` 开头加 `if (!referee_recv_info) { vTaskDelete(NULL); }` 兜底。**推荐 ①+兜底同时做**。

**P0-2 ~ P0-6 的共同根因：**这套结构体来自 2022/2023 版协议，2026 版改了 5 条数据的长度与语义，而代码只更新了 `referee_protocol.h` 的注释文字（注释里仍写着旧长度），没有同步“结构体 / 长度宏 / 解析分支”三处。修复方式见第 10.1 节，一次性按 2026 版重写即可。

## 10 修改建议与执行顺序

### 10.1 第一步：按 2026 版重写结构体与长度宏

把 5 个 P0 一次改完。改完后**加静态断言**，以后协议再变会在编译期报错而不是运行期静默出错。

```text
/* ---- 2026 V2.0.0 对齐版（替换 referee_protocol.h 对应段）---- */

#define LEN_game_robot_HP     20   // 0x0003

#define LEN_power_heat_data   14   // 0x0202

#define LEN_game_robot_state  17   // 0x0201

  uint16_t ally_1_robot_HP, ally_2_robot_HP, ally_3_robot_HP, ally_4_robot_HP;

  int16_t  damage_difference;                          // 有符号！

  uint16_t ally_7_robot_HP, ally_outpost_HP, ally_base_HP;

  uint16_t enemy_outpost_HP, enemy_base_HP;

} game_robot_HP_t;

typedef struct {                             // 0x0201 17 B

  uint8_t  robot_id, robot_level;

  uint16_t current_HP, maximum_HP;

  uint16_t shooter_barrel_cooling_value, shooter_barrel_heat_limit, chassis_power_limit;

  float    bullet_speed_limit;                        // 2026 新增

  uint8_t  power_management;                     // bit0/1/2

typedef struct {                             // 0x0202 14 B

  uint16_t reserved0, reserved1; float reserved2; // 前 8 B 保留，勿再当电压/电流/功率

  uint16_t buffer_energy;

  uint16_t shooter_17mm_barrel_heat, shooter_42mm_barrel_heat;

} power_heat_data_t;

typedef struct { float x, y, angle; } robot_pos_t;    // 0x0203 12 B（angle：度，正北 0）

typedef struct {                             // 0x0204 8 B

  uint8_t recovery_buff; uint16_t cooling_buff;

  uint8_t defence_buff, vulnerability_buff; uint16_t attack_buff;

  uint8_t remaining_energy;

} buff_t;

/* 编译期守门：结构体与长度宏不符立即报错 */
```

### 10.2 第二步：解析器加固

```text
static void JudgeReadData(uint8_t *buff, uint16_t size)   // 增加 size 入参

{

  if (!buff || size < LEN_HEADER) return;

  if (buff[0] != REFEREE_SOF) return;

  if (!Verify_CRC16_Check_Sum(buff, frame_len)) return;

  uint16_t cmd = (uint16_t)buff[5] | ((uint16_t)buff[6] << 8);

  /* switch 分支里：memcpy 前先确认 data_len 与该命令码的 LEN_* 相等 */

  /* 多帧：改成 while 循环 + 剩余长度判断，替换原递归 */

}
```

要点：① 用 16 位长度，兼容 0x0310 的 300 B；② 用 `size` 做上界，避免 DMA 半包时越界；③ 每帧再核对 `data_len` 是否等于该命令码的 `LEN_*`——“长度不符”本身就是最好的异常检测；④ 递归改循环，杜绝噪声导致的栈溢出。
